DocuBite UX Audit

Live walkthrough of the local build (landing, sign-in, dashboard, Extraction, document detail, Bills, Sheets, Automation) audited against Nielsen's 10 heuristics, the cognitive-load → conversion model, and the 12 visual-craft rules.

⚠️
Several issues to address. The visual system is coherent and most states are designed — but the document lifecycle is described in four competing vocabularies, several empty states actively mislead, and one real crash reached the generic error page during the walkthrough.

Heuristic review (Nielsen)

HighH4 · Four vocabularies for one lifecycle

The same pipeline is named differently on every surface: tabs say Processing / To review / Ready, status chips say reviewed, the stat strip says ready / auto-pushed / extracted, and Automation says Ready to sync / Blocked by a failed check / Waiting to be evaluated. Worst case observed: the strip reads “0 ready” directly beneath a tab labeled “Ready 7” — two different definitions of “ready” two lines apart.

components/pipeline/pipeline-shell.tsx:53 vs the stage tabs; Automation overview cards.

HighH1/H9 · Misleading and dead-end empty states

  • Extraction’s default tab (Processing) with zero documents says “Documents are being processed” — it claims work is happening when nothing is. (components/pipeline/document-list.tsx:56)
  • Bills with no data at all says “No bills match the current filter” under the default All filter — the user hasn’t filtered anything. (bills/page.tsx)
  • The crash page (“Oops! Something went wrong… our team has been notified”) offers only Go Home: no error reference, no retry, no support path.

HighH9 · Real crash reproduced: stale identity link hard-crashes the whole app shell

Signing in as the seeded demo user whose local row pointed at an outdated Supabase identity threw email_already_linked_to_different_identity from models/users.ts:73 — and because AppLayout calls getCurrentUser, every page rendered the generic crash screen with no recovery path. A guarded auth conflict deserves a designed screen (“this email is linked to another sign-in — contact support / sign out”), not the 500 boundary. (Worked around locally by re-pointing users.supabase_user_id.)

MedH6 · Table promises data it doesn’t show

On the Ready list, TOTAL renders “—” and READINESS is blank for all 7 seeded documents even though the extractions contain totals (Acme Corp: 5175.00 shows fine on the detail page). Either surface the values or drop the columns — an all-dash column trains users to ignore the table.

MedH4/H8 · “Approvals” exists twice in the sidebar

The sidebar has Approvals (→ /automation/approvals) and Automation, whose page repeats an Approvals tab. Two entries, one destination family — pick one home and cross-link from the other.

MedH2 · Vocabulary drift from the user’s world

  • Automation subtitle: “How much of the last 30 days of coding went through…” — GL coding is right for AP, but sitting alone it reads as software development; “invoice coding” disambiguates for one extra word.
  • Document detail asks “What type of document is this? Expense / Sale / Bank Statement / Other” while the rest of the product says Bills, invoices, receipts — the chips don’t use the nouns the app taught two screens earlier.

LowH1 · Slow navigations feel dead in dev

Route changes routinely took 10–60 s (cold Turbopack compiles on the memory-constrained machine) with no in-app pending indicator; loading.tsx boundaries exist, so verify skeletons actually show on production latencies — the sidebar item doesn’t take an active state until the new page commits.

GoodWhat’s already working

  • Bulk actions (Store to Library, Delete…) correctly disabled until a row is selected; destructive Delete is visually distinct and confirmed via dialog.
  • Sheets’ empty page is a model empty state: three concrete creation paths, one carrying a live “7 documents ready to pull in” badge.
  • Responsive layout exists (bottom tab bar at narrow widths); dialogs use a disciplined two-step z-index scale, not an arms race.

Cognitive load → conversion

Extraneous load found

  • Eight identical “Extracted” badges on the document detail — one per field. A single “All 8 fields extracted” note (with badges only on low-confidence fields) inverts the signal so attention lands where review is needed.
  • Dashboard repeats itself: the three big stat cards (Documents this month / In review / Ready) are immediately followed by a strip re-stating the same three numbers (Added / Review / Sheets). Same figures twice on one screen, two label sets.
  • Ready-tab toolbar mixes a setting with actions: “7 documents ready · Auto-stored to Docu Library after [24 hours ▾] · Push to Docu Library · Push to Accounting” packs a persistent workspace setting (retention dropdown) between one-shot actions in a single green strip. The setting belongs in Settings or behind a gear.

Mental-model gaps

  • Landing on Processing (empty) when all content sits in Ready forces the first click to be navigation recovery. Default the stage to the first non-empty tab.
  • “Touchless rate”, “auto-pushed”, “published untouched” — three coinages for the same concept across Extraction and Automation.

Offloading opportunities

  • Automation’s hero bar chart renders as one undifferentiated gray bar at 0% with a three-item legend; at the empty/zero state, replace it with a sentence (“Nothing has qualified for touchless publishing yet — suppliers earn trust after 3 reviewed documents”) that the Supplier-trust card already writes well.
  • Date fields show 15/07/2026 in the detail while lists say “4 minutes ago” — fine, but currency and totals should be computed onto the list (see H6) so users don’t open 7 documents to compare amounts.

Landing page

Verdict: ✅ strong, with three fixable gaps. Full-length pass (hero through FAQ and closing CTA).

What's genuinely good — keep all of it

  • Honesty as a feature: “Not on the list, on purpose: DocuBite does not move money, does not issue cards, does not hold funds” — a limitation presented as the reason it works across SA/Lesotho/Namibia/Eswatini. Model Rams-principle-6 copy.
  • The closing CTA is the best conversion copy on the page: “Start with one messy folder. Upload the worst one you have. If the report doesn't tell you something you didn't know, you've lost ten minutes.” Low commitment, falsifiable promise.
  • Product mockups carry the trust model: the extraction demo shows a PO field held back at 61% confidence (“waiting for you rather than sitting in your books”) — the AI's fallibility handling is demonstrated, not claimed. The app itself should be this explicit (see AI review).
  • Hero CTA pairing (“no card required · private encrypted storage”), the by-hand-vs-DocuBite three moments, and FAQ questions that are the real questions (“Does DocuBite move money?”).

Gaps

  • No pricing signal anywhere (high). A finance buyer's first qualification question is unanswerable on the page — no price, no tier names, no “from R…/mo”. On a 12-screen page that otherwise answers everything, silence on price reads as “expensive” and pushes qualified SMBs to bounce rather than book a demo.
  • Two competing narrative spines back-to-back (medium): “The AP loop — seven steps” is immediately followed by “Three steps, and none of them is data entry.” Same product, 7-step and 3-step mental models in consecutive sections. Pick one as the page spine and demote the other to a detail.
  • No social proof (medium): no customers, numbers, or testimonials on the entire page — every trust claim is self-asserted. Even one concrete figure near the commitment point (“X documents processed”, a pilot customer quote) would carry more than another feature section.
  • Implementation jargon leaks (low): the multi-currency section names Frankfurter and fxratesapi — rate-provider plumbing buyers don't need; “Provenance” as a nav label is archivist vocabulary for an SMB audience (“Where numbers come from” is the section's own, better, phrasing).
  • Only two CTA locations (low) — hero and footer, ~12 screens apart; add one after the AP-loop section.

The connective insight: the landing page already names the lifecycle better than the app does — Capture → Code → Check → Match → Approve → Sync → Pay-ready. The app's four-vocabulary problem could be solved by adopting the marketing page's own seven words (or the proposal's five) as the single glossary, so the product a user meets after the trial matches the story that sold them.

Accessibility (WCAG 2.1 A/AA)

Verdict: accessibility risks to fix. The foundation is real — html lang="en", no alt-less images, 38 components carry aria-labels, dialogs declare role="dialog"/"alertdialog" + aria-modal, toasts go through sonner (which announces politely).

Likely WCAG issues

  • No skip link — 2.4.1 A. The 11-item sidebar precedes main content on every page; keyboard users tab through it every time.
  • Focus visibility gaps — 2.4.7 AA. Only 6 files use focus-visible; bare outline-none without a focus replacement on the search inputs (search-client.tsx:46, global-search.tsx:88, add-documents-dialog.tsx:101) — verify the wrapper carries a focus ring.
  • Placeholder-only labels — 3.3.2 A. “Folder name” (files-browser.tsx:402), “Add people by email” (share-dialog.tsx:116), and the search fields have no persistent label.
  • No live regions — 4.1.3 AA. Zero aria-live/role="status" in components; extraction progress and stage-count changes are not announced (sonner covers only toasted events).

Needs implementation verification

  • components/ui/dialog.tsx has correct roles but no visible focus trap, initial focus, or focus return — keyboard-trap/focus-order risk (2.1.2, 2.4.3).
  • Contrast of the smallest gray metadata (“4 minutes ago”, stat-strip labels) against 4.5:1 — measure before claiming a failure.

Dieter Rams review

Core job: get a supplier's bill from an email into the ledger, coded and approved, with as few human touches as trust allows.

The one edit: delete the redundancies (duplicate nav entry, repeated dashboard strip, per-field badges) — the strongest Rams move here is subtraction, and all three are deletions.

Persuasive UX (Fogg's 7 tools)

  • Self-monitoring — the supplier-trust ladder is the product's best motivation mechanic but lives as prose at the bottom of Automation. → Show per-supplier progress (“2 of 3 reviews until Acme publishes untouched”) on the Vendors tab and in the review flow. Why it works: reviewers see each review buying future automation, which reframes review work as progress rather than toil.
  • Conditioning — the first touchless publish is the product's “aha” and currently passes silently into a stat. → Celebrate it once, lightly (a toast naming the supplier and what earned it). Why it works: reinforces the exact behavior (consistent review) that feeds the automation loop.
  • Suggestion — the dashboard's “Set up supplier rules to auto-code documents” nudge appears when spend is empty, i.e. before it's actionable. → Move the prompt to the moment a second document from the same supplier is coded by hand. Why it works: kairos — the prompt lands exactly when the user has just done the thing the rule would automate.
  • Flag: no dark-pattern risk found — no fake urgency, pre-checked options, or roach-motel flows on any audited screen.

AI product review (general-design-review lens)

Verdict: needs work — controls are genuinely strong, disclosure is thin.

  • Control (strong — keep): the sheet assistant uses write-then-undo with a persistent pending-changes bar (components/assistant/pending-changes-bar.tsx), and finance actions use confirm-before-execute proposals (finance-proposal.tsx) — textbook governors, correctly calibrated (cheap cell edits get undo, ledger writes get approval).
  • Trust (gap): no “AI can make mistakes”-class caveat exists anywhere in the assistant or sheet components (grep confirms), and extraction confidence is shown per field in the detail but never rolled up into the list's blank READINESS column — the one place a reviewer would triage by it.
  • Scope/steering (verify): no visible stop/abort control in the assistant panel while a chained tool loop runs; verify a user can interrupt a long run.
  • Disclosure (adequate): the =AI() formula and assistant are plainly AI by name and context; automation results are logged per document (footprints via the Activity page).

Design analysis (measured tokens)

Measured from the code rather than screenshots (same data, exact values): accent emerald-600≈#059669 family with soft tints for chips; neutrals are the Tailwind slate ramp plus custom hairlines #e6ebf1/#dbe3ea; type is Inter (5 weights, self-hosted) + a display face via CSS variables; spacing observed on the 4px scale throughout; radius vocabulary rounded-lg/xl + one rounded-[11px] outlier (account-menu.tsx:45); elevation = hairline borders, with shadow reserved for menus/dialogs (shadow-2xl) — consistent with the craft findings. Feature-prioritization remains the one unrun skill: its weighted matrix needs business weights (revenue impact vs. churn risk vs. compliance) that only you can set; the effort×reward grid below is the code-informed substitute.

Document journey (research & strategy pass)

Problem statement (Double Diamond, Define): A bookkeeper processing supplier bills needs to see where each document is in its lifecycle and what is blocking it, because the product presents seven parallel destinations (Extraction, Bills, Sheets, Docu Library, Accounting, Approvals, Automation) for what is actually one linear flow — so they carry the pipeline in their head instead of seeing it on screen.

Actor: Naledi (proto-persona below) — owner-bookkeeper, does the books alone in one Friday-afternoon sitting. Scenario: supplier bills arrived by email through the week; she expects to clear all of them in one session and end knowing nothing slipped. One map, one actor — the team variant follows.

Team variant — Thabo (AP clerk) with Lerato (controller): same phases, two differences. Review is daily queue work, not a weekly batch — so list triage (amount, due date, confidence) matters more than batch totals. And Approve & match splits across people: Thabo's low point isn't finding status for himself but answering for it (“where is the CloudHost bill?” — see storyboard), and Lerato's entire product experience is the approval surface, so approvals buried inside Automation buries her whole product. The proposed stage indicator serves both maps: for Naledi it collapses stages she performs alone into one glance; for Thabo it names who holds the document (“Awaiting approval — Lerato”).

Opportunities (mapped to phases):

  • Arrive/Extract: land on the stage with content; make the inbound-email receipt visible (“received 2 min ago, extracting”).
  • Review: roll per-field confidence up into the list so the reviewer triages by it (the blank READINESS column's real job).
  • Approve & match (the valley): restructure the nav so lifecycle stages are one “Documents” spine (Inbox → Review → Approve → Ready to pay → Done) and Library/Sheets/Accounting/Automation become secondary sections; give every document a stage indicator on its detail page (“Extracted ✓ → Checks ✓ → Awaiting approval → Sync → Pay”). This single change dissolves the duplicate-Approvals nav and forces the one-glossary fix.
  • Sync & pay: the bill row should carry its ledger-sync state inline rather than asking the user to cross-check Accounting.

Proto-personas (inferred — validate with interviews)

Per ux-personas' own rule these are proto-personas: inferred from the product's framing (AP loop, ZA EFT payment runs, QuickBooks/Xero/Bigcapital sync) and typical accounting/finance roles, not from user research. They cover the two shapes the product must serve: one person wearing every hat, and a team where stages are different people.

Naledi, 38 — owner & bookkeeper, 6-person services firm

“I do the books on Friday afternoons. If something needs chasing, it waits a week.”

  • Goals: clear every bill in one sitting; trust that nothing slipped; hand her accountant a clean ledger.
  • Frustrations: can't tell at a glance what still needs her; anything that takes touring multiple pages doesn't fit a Friday-afternoon session.
  • Behaviors: forwards supplier emails as they arrive, processes in one weekly batch; approves her own work (approval routing is overhead to her).
  • Context: laptop, weekly, alone — she is uploader, reviewer, approver, and payer. The lifecycle spine must collapse gracefully when every stage is the same person.

Thabo, 29 — AP clerk, 80-person company, finance team of 3

“My job is the queue. If the controller asks where an invoice is, I must answer in one look.”

  • Goals: empty the review queue daily; route bills over threshold to the controller; never be the reason a supplier calls.
  • Frustrations: status scattered across Extraction, Approvals and Bills; “0 ready under Ready 7” type contradictions make him distrust the counts he reports upward.
  • Behaviors: in the product daily; lives in lists; triages by amount and due date — which is why the blank TOTAL column hurts him most.
  • Context: desktop, all day. He hands off to Lerato (controller, 45) who only ever opens the product to approve — her entire experience is the approval surface, so a buried Approvals page is her whole product being buried.

What to fix first (effort × reward, code-checked)

Do first — low effort, high reward

  1. Fix the two lying empty states — copy-only edits in document-list.tsx:56 and the Bills page string. Pays off because they sit on every new user's first screen.
  2. Rename the stat-strip “ready” — one line in pipeline-shell.tsx:53; kills the “0 ready under Ready 7” contradiction today, ahead of the full glossary work.
  3. Default Extraction to the first non-empty stage — the stage is already a URL param the server page reads; pick the default from the counts it already fetches.
  4. Add a skip link + focus rings on the three bare inputs — one layout element and three class edits.
  5. Drop the duplicate sidebar “Approvals” entry and the dashboard's repeated stat strip — deletions, not builds.

Do next

  • Collapse the 8 “Extracted” badges — low effort (single field-row.tsx render), medium reward.
  • Replace transition-all in 9 components — low effort, mechanical; low-medium reward.
  • Designed screen for the identity-conflict error — medium effort (catch in lib/auth.ts + one page), high reward: it currently takes down every route.
  • Dialog focus management — medium reward, and looks hard, isn't: every dialog flows through the one components/ui/dialog.tsx, so trap/restore lands everywhere at once.

Plan it in

  • One lifecycle glossary — high reward but real work: tabs, chips, stat strip, six Automation cards, and marketing copy all carry stage names; do it once, with a written glossary, not piecemeal.
  • TOTAL/READINESS columns — looks easy, isn't: the detail page has the totals but the list doesn't, so the list query/serializer isn't carrying extracted fields; that's a data-path change plus a decision about which field is “the” total per template.

Skip for now

  • Flattening the sidebar/assistant gradients — both are near-invisible; cheap but near-zero payoff.
  • Relocating the auto-store retention dropdown — annoying placement, but wait for the Settings IA to firm up rather than moving it twice.

  • components/ui/dialog.tsx: initial focus to the dialog, focus trapped while open, returned to the opener on close, Escape closes — one shared component fixes every dialog.

5 · Deletions (Rams edit)

  • Sidebar: remove the standalone Approvals entry; Automation keeps its Approvals tab (or, with the nav restructure, both fold into the Documents spine).
  • Dashboard: delete the Added/Review/Sheets strip that restates the three stat cards above it.
  • Document detail: replace 8 per-field “Extracted” badges with one line — “All 8 fields extracted” — and badge only low-confidence fields (“Check this · 61%”), matching the landing page's own demo.

  • Flatten the two decorative gradients (sidebar.tsx:128 → solid #f1f5f8; assistant header → solid emerald-50).

Priority actions

  1. Unify the lifecycle vocabulary. One glossary — e.g. Processing → Needs review → Ready → Published — used by tabs, chips, stat strips, and every Automation card. Rename the strip’s “ready” (it means published untouched) so “0 ready” can never sit under “Ready 7”. Impact: high — this is the product’s core object.
  2. Fix the three lying/dead-end states. Inbox empty copy (document-list.tsx:56), Bills unfiltered-empty copy, and a designed screen for the email_already_linked_to_different_identity conflict instead of the app-wide crash page. Impact: high — first-session trust.
  3. Land users on content. Default the Extraction stage to the first non-empty tab, populate or remove TOTAL/READINESS, and move the auto-store retention dropdown out of the action strip. Impact: medium.
