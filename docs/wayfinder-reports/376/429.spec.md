# Spec — Build: per-line Accounts, guessed Default account and supplier account rules (#429)

Source: ADR 0011 / #402 resolution. Ownership: DocuBite (Owner decides Default/rules).
Status: Ready for build. Scope: QuickBooks + Xero (Sage inherits via its own provider build, #430 area).

## Problem & user need

Today `IntegrationConnection.defaultExpenseAccountId` is one account for every line of every
bill (`lib/integrations/{quickbooks,xero}/bill-mapper.ts`, doc comment: "no per-line mapping").
`CategoryAccountMapping` lets an Owner override by free-text category, but nothing is guessed and
nothing learns. A reviewer who wants a line coded correctly must fix it after the fact in the
ledger. This ticket makes the account a first-class per-line fact, guesses the Default once at
connect, and learns a supplier's usual account from what gets approved — so most lines never need
a touch.

## Data model changes (`prisma/schema.prisma`, additive migration)

- `Document` line items gain an `accountExternalId` per line. Line items today live inside
  `codingData`/`reviewedData` JSON (no line-item table) — add `account_external_id` (and
  `account_source: "supplier" | "default_guessed" | "default_confirmed" | "manual"`) to each line
  object; document in the `codingData` comment block (~line 601) alongside the existing coding keys.
- `IntegrationConnection` gains `defaultExpenseAccountGuessed boolean @default(true)` — flips to
  `false` the first time an Owner saves it or a post confirms it. `defaultExpenseAccountId/Name`
  are unchanged in shape but are now written by the connect-time guess, not left null.
- New `SupplierAccountRule` model: `workspaceId`, `connectionId`, `supplierName` (or an FK if a
  Contact/Vendor entity exists — check `AccountingEntity` kind `"vendor"`), `accountExternalId`,
  `lastUsedAt`, `createdAt`, `updatedAt`. Unique on `[connectionId, supplierName]`. Mirrors
  `CategoryAccountMapping`'s shape (same file, `prisma/schema.prisma` ~2155-2172).
- `CategoryAccountMapping` is kept, read-only translation for categories written before the ledger
  was connected (per #402 point 1: "survives only to translate categories written before
  connection"). No new rows are created by this ticket's flows.

## Backend changes (kind: backend)

1. **Chart sync on connect** — `lib/integrations/sync.ts` already syncs `AccountingEntity` rows
   (accounts/vendors/tax rates). Call it from the connect completion path
   (`app/(app)/workspaces/[workspaceId]/integration-connection-actions.ts`) right after Nango
   reports success — today nothing calls it there (the docstring promises this, the code doesn't
   do it). On failure, leave `defaultExpenseAccountId` null and let the Default row show the
   retry state (surface step).
2. **Default account guess** — after a successful chart sync, exact-match the connection's synced
   expense-type `AccountingEntity` rows against the provider's catch-all name (`"General
   Expenses"` for Xero, `"Uncategorized Expense"` for QuickBooks — Sage name from #428's research,
   out of this ticket). No match → leave both fields null, `defaultExpenseAccountGuessed` stays
   `true`. Write this as a pure function (`lib/integrations/{quickbooks,xero}/default-account-
   guess.ts`) taking the synced `AccountingEntity[]` and returning the match, so it is testable
   without a live provider call.
3. **Per-line account resolution** — `lib/finance/actions.ts`'s existing "mappings → category map
   → default" chain becomes, per line: supplier rule (if the doc's vendor has a
   `SupplierAccountRule` for this connection) → Default account. The `CategoryAccountMapping`
   check only applies to lines whose `codingSource` predates connection (pre-connection
   category). Populate each line's `account_external_id`/`account_source` on this resolution,
   *once*, when the document reaches the state the pre-fill currently runs at (check
   `lib/finance/actions.ts` for the exact trigger — likely on entering review).
4. **Bill mappers post per line** — `lib/integrations/quickbooks/bill-mapper.ts` and
   `lib/integrations/xero/bill-mapper.ts` change from a single `accountRef` parameter to reading
   `accountExternalId` off each `NormalizedLineItem` (extend `NormalizedLineItem` in
   `lib/integration-bill-mapping.ts` with `accountExternalId: string`). A line with no account is
   a mapping error (`BillMappingError`) — post eligibility (`lib/integration-push-selection.ts`'s
   `resolveSelectionEligibility`) gains "every line has an Account."
5. **Supplier rule learned on approval** — wherever a document's `status` transitions to approved
   (grep `status.*approved` in `lib/finance/actions.ts` / `lib/workflow`), upsert
   `SupplierAccountRule` with the account of the line with the largest `amount`, and bump
   `lastUsedAt` on every later push that uses the rule.
6. **Archived-account fallback** — a line/Default whose `accountExternalId` no longer matches an
   active `AccountingEntity` (deactivated flag, per the model's doc comment ~2133) falls back to
   the Default and is flagged for the surface layer to say so; an archived Default itself blocks
   posting (surface: notice above the queue).
7. **Post dialog eligibility & override removal** — `postSelectedDocumentsAction`
   (`app/(app)/workspaces/[workspaceId]/post-selected-documents-actions.ts`) drops the
   `accountOverrides` parameter and `filterOverridesToEligible` call entirely; per-line accounts
   are already resolved before the dialog opens.

Each backend step ships with its own red-first test (bill-mapper tests already exist and gain
per-line-account cases; new tests for the guess function, the resolution chain, and the learn-on-
approval upsert). `simplify` + `/code-review` at each step's close per `CODING_STANDARDS.md`.

## Surface changes (kind: surface)

### A. Detail pane — per-line Account (`components/pipeline/document-detail/line-items-section.tsx`)
Each line gets a native `<select>` (pattern: `field-row.tsx`), `code · name`, `<optgroup>` per
account type, sourced from the connection's synced `AccountingEntity` rows (expense + a scoped set
appropriate to the doc's line, per #402). Below/beside the select, a one-line provenance string in
words, not a badge alone:
- `"Acme's usual"` — a `SupplierAccountRule` match.
- `"Default · guessed"` — the connection Default, still `defaultExpenseAccountGuessed = true`.
- `"Default · Acme's usual is archived in Xero"` — the rule's account is archived, fell back to
  Default.
Before approval, a line whose account differs from the supplier's existing rule shows, under the
select: `"Becomes Acme's usual when approved"` — no toast; the pane's own advance on approval is
the feedback (per #402: "there is no toast, because the pane advances").

### B. Accounting page — Default row + Supplier accounts table
(`app/(app)/workspaces/[workspaceId]/admin/integrations/page.tsx`,
`components/settings/category-account-mapping-table.tsx` as the layout precedent)
- **Default row**: shows the guessed/confirmed account; **Guessed** badge is neutral (slate, not
  amber — amber is reserved for attention states per craft-floor). States: `"Reading your chart of
  accounts…"` while sync runs; `"Couldn't read the chart of accounts from Xero. [Try again]"` on
  failure (provider name interpolated).
- **Supplier accounts table**: columns Supplier · Usual account · Last used · Change / Forget.
  Filter box appears above 20 rows (reuse the pattern, not a new component, if one exists —
  check `components/ui` for an existing filterable-table affordance before building one). Empty
  state copy: `"Supplier accounts fill in as documents get approved — the account of the largest
  line becomes that supplier's usual."` An archived account's row says so inline next to Usual
  account, e.g. `"General Expenses (Acme's account was archived in Xero)"`.

### C. Post dialog (`components/queue/post-confirm-dialog.tsx`)
- Remove the per-row `extraColumn` account-override `<select>` (lines ~81-88) and its `accounts`
  state (~line 33) entirely — accounts are resolved per line before the dialog opens.
- Add, shown only on the company's first post and any post while the Default is still guessed:
  `"Lines with no supplier account go to **General Expenses** (guessed). [Change]"` (provider's
  account name interpolated). `[Change]` opens the Default editor (Accounting page) or an inline
  editor — decide at `shape` time which is cheaper without a new route; writes
  `defaultExpenseAccountId`/`Name` and flips `defaultExpenseAccountGuessed` to `false`.

### D. Queue eligibility mark
Wherever "Ledger ready"/ineligible reasons are shown per row (`components/queue/document-queue.tsx`,
`invoice-queue.tsx`), add the reason `"needs an Account"` for a line missing one.

## Fortify — state inventory

- Chart sync: pending / succeeded / failed(retry).
- Default: no match found (blank, Guessed) / guessed+matched / confirmed (Owner saved or post
  confirmed) / archived (blocks posting, queue notice).
- Per line: has supplier rule / has guessed default / manual override / archived fallback / no
  account (blocks post eligibility for that document).
- Supplier rule: none yet (empty state) / present / account archived (falls back, row says so).
- Post dialog: first post ever / default still guessed / default confirmed (banner suppressed).
- Correction-adjacent (out of this ticket, #430): none — this ticket only touches future posts.

## Ethical review

No dark pattern: the Guessed badge and the post-dialog banner are disclosure, not persuasion —
they tell the Owner a machine picked this and offer an easy correction, never hide the guess or
make "Change" harder to find than "Continue". Cleared against the anti-pattern catalog (no
confirmshaming, no forced continuity, no hidden cost).

## Build plan (steps for the build phase, one per session)

1. `kind: backend` — schema migration (`SupplierAccountRule`, `defaultExpenseAccountGuessed`,
   per-line `account_external_id`/`account_source` in `codingData`), additive only. Check:
   `prisma migrate dev` clean, existing tests green.
2. `kind: backend` — chart sync on connect + Default guess function + tests.
   Files: `integration-connection-actions.ts`, new `default-account-guess.ts` (x2 providers).
3. `kind: backend` — per-line resolution chain + bill mapper per-line posting + post-eligibility
   change + accountOverrides removal from `postSelectedDocumentsAction`. Files: `lib/finance/
   actions.ts`, both `bill-mapper.ts`, `integration-bill-mapping.ts`,
   `integration-push-selection.ts`, `post-selected-documents-actions.ts`.
4. `kind: backend` — learn-on-approval upsert + archived-account fallback resolution + tests.
5. `kind: surface` — Detail pane per-line Account select + provenance line + pre-approval hint.
   `impeccable shape` → `clarify` → `polish`. Read `craft-floor.md` first.
6. `kind: surface` — Accounting page Default row states + Supplier accounts table (+ filter,
   empty state). Same Impeccable sequence.
7. `kind: surface` — Post dialog: remove per-row override, add first-post/guessed banner + queue
   ineligibility reason.
8. `kind: surface` (build gate) — detector before/after (`impeccable detect --json`, in-page
   overlay against dev server), `evaluate`, `critique` per the closing bar in
   `docs/agents/design-tickets.md`.

Each backend step: test written red first, `simplify`, no-`lib/`-edit-without-a-test hook
satisfied. Each surface step: craft-floor read, detector run on the changed surface before commit.
