## Findings: document-first capture tools (Dext Prepare, Hubdoc, AutoEntry)

Sources: [Dext — publish to QuickBooks Online](https://help.dext.com/en/articles/377056-how-to-publish-documents-from-dext-to-quickbooks-online), [Dext — supplier/customer rules](https://help.dext.com/en/articles/216125-how-to-use-supplier-and-customer-rules-in-dext), [Hubdoc — How it works](https://www.hubdoc.com/how-it-works), [Hubdoc — vendor rules & posting to Xero](https://learn.hubdoc.com/courses/66202/lectures/971591), [AutoEntry — accounting software integration](https://help.autoentry.com/en/articles/1312817-autoentry-and-integration-with-accounting-software), [AutoEntry — bank statement extraction](https://www.autoentry.com/bank-statement-extraction-software), [Books Automator — Dext Prepare integration guide](https://booksautomator.com/guides/dext-prepare-integration/).

**1. Separate publish view, or per-document?** All three publish **per document**, not through a cross-type "ready to publish" queue. Dext's Costs/Sales inbox is reviewed and published item-by-item (or via bulk-select of already-reviewed items — still a filter on the same inbox, not a distinct surface). Hubdoc and AutoEntry follow the same shape: capture → code/review in the document's own record → publish that record. None of the three docs surfaced a dedicated staging list that spans document types the way a "ready to publish" screen would — publish readiness is a status on the document, not a place.

**2. Connection/publishing settings.** Dext: publish destination per cost item (Bill/unpaid, Cash, Check, Credit Card/paid), credit-note flag, tax default required for publish, "auto-publish all items" toggle (sends to QuickBooks automatically once marked ready), source image always attaches to the posted record. Hubdoc: "Publish As" setting per supplier (bill vs. other transaction type) plus Supplier Rules that carry the coding forward automatically. AutoEntry: per-supplier default category + VAT code, learned/remembered rules applied to future documents from that supplier. All three attach the source document to what they post — this is a hard floor in the category, not a nice-to-have.

**3. How are defaults first set up?** All three are **learned from history / set by the user on first encounter**, not guessed from the chart of accounts up front. Dext and Hubdoc: the user (or accountant) sets a Supplier Rule the first time a supplier's document is coded, or account-level defaults apply until overridden; the rule then auto-applies to every later document from that supplier. AutoEntry: explicitly "remembers" the coding chosen and reapplies it next time, or the account manually sets a default category per VAT code for a supplier. None of the docs describe an upfront bulk guess against the full chart of accounts at connect time — the guess is per-supplier and earned by use, not produced en masse on day one.

**4. Correcting a wrong account after publishing.** None of the vendor documentation addresses this directly (help-centre gap, not a design absence — Dext's article is silent, and general web results didn't surface a definitive answer for any of the three). The working assumption from adjacent QuickBooks/Xero documentation is the general SaaS-integration pattern: fix it in the ledger (the posted bill/transaction is now a ledger object, not the capture tool's), since a re-publish would risk a duplicate. This is not confirmed with a primary source and should be treated as unverified if DocuBite's "nothing un-posts" design depends on it.

**5. Bank statements.** AutoEntry explicitly extracts data from bank statements and can auto-fetch from bank feeds, publishing to Xero/Sage/QuickBooks or CSV. Hubdoc's own marketing copy lists statements alongside receipts and bills as a document type it "codes," but the docs pulled don't distinguish statement handling from bill handling — no evidence it posts statement lines as transactions the way a bank feed would; more likely it stores/attaches the statement as a document rather than transacting off it. Dext's docs (this session) didn't surface statement-specific behaviour at all.

## Where DocuBite's position stops the pattern from transferring

- **WhatsApp intake, LS/ZA:** none of these three tools take WhatsApp as an intake channel or operate in Lesotho/South Africa — irrelevant to how they split capture from ledger, so no correction needed here, but it means there's no existing WhatsApp-first capture-to-ledger pattern to borrow; DocuBite's WhatsApp path is its own design.
- **Nothing un-posts (map Notes):** the vendors' silence on post-publish correction (finding 4) can't be borrowed as "edit and re-sync" without contradicting DocuBite's own rule that a disconnect never un-posts and nothing burns a duplicate attempt. DocuBite's posted-record correction path, if it needs one, has to be designed fresh, not copied.
- **Per-supplier learned defaults (finding 3) transfer directly** and match what the map's Notes already decided: "pull the chart of accounts at once and *guess* the default expense account + category mappings, shown as editable defaults" — DocuBite's plan is a bulk first guess at connect time (day one), which is *more* upfront than any of the three vendors do (they earn the rule per supplier as documents arrive). This is a deliberate DocuBite deviation, not something contradicted by the research — flagging it for the guessed-defaults ticket rather than treating it as a gap.
- **Per-document publishing (finding 1) matches DocuBite's typed-queue design already**: Invoices, Purchase Orders, Receipts, Bank Statements each post from their own queue (`CONTEXT.md` — "a document is posted from its own queue and stays there as a Posted row"). No cross-type "ready to publish" surface is needed; the pattern the vendors use is already DocuBite's shape.
- **Bank statements (finding 5) is the least certain finding** — AutoEntry treats statements as an extraction+publish source, but whether that means posted bank transactions or just an attached record isn't confirmed from primary docs. DocuBite's own Bank Statements queue exists to reconcile the Paid mark from statements/remittances (map Notes: "it learns what was paid from documents... not from its own rails"), which is closer to Hubdoc's likely attach-only behaviour than to a bank-feed transaction import — worth a closer look if the guessed-defaults or bank-statements ticket needs it, but not blocking here.

No score — this is a research ticket, not a rendered surface.
