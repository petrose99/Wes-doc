### Real findings to fix in the close-phase batch (all three readers converge on the same set)

1. **[P1] `g d` (Admin) drops focus to `<body>` instead of `#main`.** `keyboard.json` →
   `g-d-jump: ["body", "url:/admin/configuration"]`. Root cause found: the handler
   (`components/shell/keyboard-shortcuts.tsx` line ~88) unconditionally writes
   `sessionStorage[PENDING_FOCUS_KEY] = "rows"` for every destination including Admin, but the
   spec (§2) says "Admin → focus `#main`" as a special case, and nothing on the Admin route
   consumes `PENDING_FOCUS_KEY` at all (only `queue-screen.tsx` and `search-client.tsx` do) — so
   the flag is silently dropped and focus never moves. Fix: special-case Admin's destination entry
   to focus `#main` directly (no sessionStorage round-trip needed since it's an immediate DOM
   target), or add a consumer on the Admin route.
2. **[P1] Dialog `Esc` returns focus to `<body>`, not the spec's own `#main` fallback.**
   `keyboard.json` → `dialog-esc-focus-return: ["body"]`. Spec §2: opener resolution is "the
   element focused when `?` was pressed, or `#main` if `body`." Needs tracing into the shared
   `Dialog` primitive's `openerRef` handling — likely it captures `document.activeElement` at
   open time (which was legitimately `body` in this probe, since focus was deliberately blurred
   first to simulate an AT/browse-mode press) but never applies the documented `#main` fallback
   when that capture is `body`. Fix belongs in `components/shell/keyboard-shortcuts.tsx` (or
   wherever `openerRef` is set before calling the shared `Dialog`), not in the shared primitive
   itself, unless other `Dialog` callers should get the same fallback (check before generalizing).
3. **[P2] `/` search key: probe shows focus staying on `body` and the URL empty** (`keyboard.json`
   → `slash-focuses-search: ["body", "url:"]`). Given finding-1's false-alarm history (this route's
   first `next dev`/turbopack compile can need well over 1000ms), **re-verify with a longer wait
   (3000ms+) before treating this as a real bug** — the mechanism (`search-client.tsx` lines 24-27)
   reads correctly on inspection and mirrors the working row-arrival path exactly. If it still
   fails with a longer wait, it's a real P2.
4. **[P2] The tab-count-to-first-row headline metric (spec's ≤3, incumbent 28) was not actually
   demonstrated.** This session's probe did a raw `Tab` walk from page load (6 stops, ends on the
   "Purchase Orders" rail link) rather than exercising the prescribed "Skip to the list" link
   activation (spec §10: "skip → skip → Enter"). This is very likely **a probe gap, not a product
   bug** — the skip link exists (`components/shell/skip-to-list-link.tsx`, wired into
   `layout.tsx`) and was never activated in this round. **Close-phase must add a probe that
   presses Tab twice then Enter on the second skip link** and confirm it lands on a row button,
   before either fixing anything or claiming the metric is met.
5. **[P3, not a #262 defect] `mismatch-nav-pane-open` capture carries 13 real detector findings**
   (6× `clipped-overflow-container`, 1× `tiny-text` 11px, 1× `cramped-padding`) versus 4-5 on every
   other state — these are pre-existing `po-compare.tsx`/pane-shell properties from #250, not
   anything #262's focus-only `]`/`[` handler introduces (it adds no DOM). Do not fix under #262;
   if worth fixing, it is a separate ticket against the pane shell. The recurring 4-5 findings on
   every single capture (`ai-color-palette` cyan gradient, `overused-font` inter, `layout-transition:
   height`, `dark-glow #ffba00`) are the same app-wide residue prior tickets (#250/#251/#261)
   already documented — not new, not #262's to fix.
6. One evaluate-reader finding not independently confirmed: **mismatch-nav bracket landing on a
   control that may be under a different tab than the screenshot shows** (Details tab visible,
   PO-compare button reported as focused). Likely a capture-timing artifact of the probe advancing
   past the tab click before the screenshot settled, not a real defect — worth a quick direct look
   in the close phase but not high-priority.
