## Real fixes landed this session (G2 continuation)
1. **Esc-focus bug (confirm-dialog.tsx)**: `MoveDocumentDialog`/`DeleteDocumentDialog`
   mount with `open` hardcoded true right after their popover unmounts, so
   `document.activeElement` was unsettled and Esc restored focus to `<body>`. Fixed
   with `openerCapturedRef` + new `restoreFocusTo` prop (confirm-dialog.tsx), wired
   through `detail-pane.tsx`'s `PaneMenu` (`triggerRef`) and both dialogs in
   `document-actions-menu.tsx`. **Verified live** via `probe297.mjs` — Esc now
   returns focus to "More actions". Round's keyboard probes now 27/27 pass.
2. **Library Move-dialog wrong exclusion (real bug)**: `MoveDocumentDialog`'s
   `currentType` was always `ctx.doc.docType` (the *resolved* type, via
   `resolveDocType`'s legacy-template fallback). A Library document with a null raw
   `docType` that only resolves to e.g. "receipt" via template code had "receipt"
   wrongly excluded from the Move target list — spec §5 requires currentType
   **unset** for Library (no real "current queue"). Fixed: added
   `moveCurrentType` computed from the *raw* `document.docType` in
   `app/(app)/workspaces/[workspaceId]/documents/[documentId]/page.tsx` (only set if
   `isDocType(document.docType)`), threaded through `SplitPane` (new
   `moveCurrentType` prop) into `useRegisterDocumentActions`'s new `currentType`
   field on `RegisteredDocument` (`components/queue/document-actions-menu.tsx`), and
   `detail-pane.tsx`'s `MoveDocumentDialog` now reads `ctx.doc.currentType` instead
   of `ctx.doc.docType`. `docType` itself (Direction row, menu visibility) is
   untouched. **Do not** add `bank_statement` to `TYPED_MOVE_TARGETS` — the code
   comment there is deliberate ("bank statement is not a move target"); the round's
   `typedCount === 3` expectation was already correct, the bug was the wrong
   exclusion, not a missing target. `tsc --noEmit` clean.
3. **"Found in Search only." caption (document-actions-menu.tsx)**: 0px vertical
   padding on 12px text — added `py-1`. This fixed the same finding on **most**
   states but **not** `04-move-dialog-target-chosen`/`04-move-dialog-other-expanded`
   (both widths) — gate still shows this exact same `cramped-padding` finding
   ("0px vertical padding (need ≥4.0px for 12px text)") on those two states only,
   meaning there's a **second** 12px-text element with no vertical padding that only
   exists once a target is chosen (or is present but only detected once the dialog
   is taller / scrolled). Not yet located — `confirm-dialog.tsx`'s description `<p>`
   is `text-sm` not `text-xs` so it's probably not that. Candidates not yet checked:
   the `confirmLabel` button text, or some conditionally-rendered text near the
   consequence line. Investigate with a probe that opens the dialog, picks a target,
   and walks all text nodes at ~12px checking computed padding (same technique as
   `probe_33.mjs` in scratch-297, but for font-size instead of content match).
