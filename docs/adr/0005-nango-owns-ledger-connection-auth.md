# 0005 — Nango owns the Ledger connection's auth; DocuBite stores no token

## Status

Accepted (Wayfinder [Ledger connection model and the Nango boundary](https://github.com/petrose99/Wes-doc/issues/382), map [Ledger connections through Nango](https://github.com/petrose99/Wes-doc/issues/376))

## Context

`IntegrationConnection` currently holds `accessTokenEnc`/`refreshTokenEnc`/`*ExpiresAt`/`scope`, and `lib/integration-token-refresh.ts` refreshes them under a row lock before every push. The map's charting decision (owner, 2026-09-22) moves QuickBooks and Xero onto Nango alongside the not-yet-built Sage connector, so DocuBite owns no OAuth code at all. This ticket draws the exact boundary: what the row keeps, what "connected" means, how a push gets an access token, and what happens to the two routes and the refresh module that exist today.

The alternative — keep decrypting/refreshing locally but source the initial tokens from Nango — was rejected: it keeps DocuBite as a second, redundant token vault (the thing #377 and #378 exist to retire) and still needs a refresh scheduler DocuBite would maintain for three providers instead of Nango's one.

## Decision

**Columns.** `accessTokenEnc`, `refreshTokenEnc`, `accessTokenExpiresAt`, `refreshTokenExpiresAt`, `scope` are dropped from `IntegrationConnection`. Added: `providerConfigKey` (Nango's integration id — `quickbooks`, `xero`, `sage`) and `nangoConnectionId` (Nango's `connectionId`; DocuBite mints and passes this as its own connection `id` at session-creation, so no extra column is actually needed beyond reusing `id` — recorded here so the build step doesn't reintroduce a second id). `externalTenantId`/`tenantName` stay: they hold the *provider* tenant (QuickBooks `realmId`, Xero `tenantId`, Sage business id), which Nango never interprets for Sage and only surfaces via `connection_config` for the other two. DocuBite still writes it itself in all three cases (QuickBooks: read off the callback via Nango's `connection_config`; Xero: `xeroPostConnection`'s `get-tenants` result read via the same `connection_config` field, chosen by the connect flow's org picker per #379; Sage: `GET /businesses` called once through the Nango proxy right after the `AUTH` webhook fires, no Nango-side field for it).

**Status vocabulary.** `status` becomes `connected` | `needs_reconnect`, matching `CONTEXT.md`'s Ledger-connection definition exactly (no `active`, no `needs_reauth` — those were implementation words leaking onto the model). *Absent* is not a status value: it is the row not existing (`findFirst` returns null), exactly as `getLedgerConnectionBandStatus` already treats a missing row today. Flips:
- `needs_reconnect` ← Nango's `AUTH` webhook, `operation: "refresh"` or `"creation"`, `success: false` (per #379's resolution) for the row matching `connectionId`.
- `connected` ← `AUTH` webhook `operation: "creation"`, `success: true` (new row created) — the webhook is the trigger; DocuBite never marks itself connected off the frontend's resolved promise, which #379 flagged as non-authoritative.
- Row deleted ← DocuBite's own disconnect action calls Nango's `DELETE /connection/{id}`; the local row is deleted in the same request (disconnect never un-posts existing `IntegrationPush` rows, which keep their `connectionId` as a historical FK — `onDelete` stays `Cascade` on the relations that are query-only projections, e.g. `AccountingEntity`/`categoryAccountMappings`, since a deleted connection's cached chart of accounts is meaningless; `IntegrationPush`/`LedgerTransaction` rows are the audit trail of what was actually posted and must survive, so those two relations move to `onDelete: SetNull`/keep `connectionId` nullable-on-delete — a schema change the build step must make, since today's `Cascade` on `pushes` would silently erase push history on disconnect).

**Access token boundary.** `lib/integration-token-refresh.ts` retires entirely — no code in DocuBite ever holds a decrypted or encrypted provider token. `lib/integrations/{quickbooks,xero}/client.ts`'s bearer-header `apiRequest` calls are replaced by Nango's proxy (`POST https://api.nango.dev/proxy/...` with `Connection-Id` + `Provider-Config-Key` headers, the shape #379 recorded) — Nango attaches the live access token server-side and refreshes it transparently; DocuBite's proxy call carries no token at all. `getValidAccessToken(connectionId)` is replaced by a much smaller `nangoProxy(connectionId, provider, path, init)` helper that needs no row lock (Nango serializes refreshes on its own side) and cannot itself throw `needs_reauth` — that state only ever arrives asynchronously via the `AUTH` webhook, never synchronously off a failed call, so `attemptIntegrationPush`'s `TokenRefreshError` branch (`integration_needs_reauth`) is replaced by reading `connection.status` before the call (unchanged behaviourally — it already checks `connection.status !== "active"` first) and a plain-retryable branch for an ordinary proxy 401 that isn't yet reflected in `status` (rare race between the webhook and a push firing) — that case is <code>IntegrationAuthError</code> exactly as today, still flips the row to `needs_reconnect` synchronously as a fallback, not only on the webhook.

**Routes.** `app/api/integrations/{quickbooks,xero}/connect/route.ts` and `.../callback/route.ts` (4 files) retire, replaced by one provider-agnostic pair: `POST /api/integrations/connect-session` (mints a Nango Connect session token, scoped to the one `providerConfigKey` the Owner picked, `allowed_integrations: [key]`) and `POST /api/webhooks/nango` (verifies Nango's HMAC signature, handles `type: "auth"` by upserting/flipping the row per the rules above; ignores other webhook types — none are subscribed, since sync/proxy webhooks are out of scope). Sage gets no bespoke route: same two endpoints, `providerConfigKey: "sage"`.

**Push pausing without burning attempts.** Today, `connection.status !== "active"` forces `forceTerminal = true`, which — per `computePushUpdate` — counts as an attempt and can exhaust `MAX_PUSH_ATTEMPTS`, ending in `failed` rather than `pending`. That is a bug relative to the map's Notes ("pauses posts (no attempts burned)"), not a Nango-shaped change, but this ticket is where it's named since the boundary work touches the same branch: `attemptIntegrationPush` must check `connection.status === "needs_reconnect"` **before** calling `computePushUpdate` at all and, on that branch, leave the push `pending` with `attempts` unchanged and `nextAttemptAt` pushed out by a fixed poke interval (5 min, not the exponential backoff curve, since nothing will succeed until a human reconnects) — no attempt increment, no lease burned twice. Reconnecting (row flips back to `connected`) does not itself requeue; the existing `nextAttemptAt` poke picks the push back up within 5 minutes, same as any other pending row.

**Cutover for existing QuickBooks/Xero rows.** One-time reconnect, not a token import: `CONTEXT.md` confirms every `IntegrationConnection` row that predates this ADR was Bigcapital-era demo/test data (no pilot firm exists yet — the map's own Notes rule out "any pilot firm" this effort), so there is no real customer grant to preserve continuity for. The build step deletes all pre-Nango rows in the same migration that drops the token columns (a destructive migration is acceptable here specifically because the data has no external users depending on continuity — flagged explicitly so a later, real cutover with live customers does not copy this precedent) and any Owner who had one connected sees "no ledger connected" and reconnects through the new flow, identical to first-time connect.

**Owner email.** Triggered by the `needs_reconnect` transition (webhook-driven, above), once per break — i.e. only on the transition into `needs_reconnect`, not on every subsequent failed push while it stays broken (mirrors `CONTEXT.md`'s "Owners are told once"). Suppressed if the row is already `needs_reconnect` (idempotent on webhook redelivery).

## Scenarios checked

- **Xero login picks one of three organisations**: the org picker is Xero's own consent screen inside the popup (#379 — Nango renders no picker); DocuBite's connect flow reads the chosen `tenantId` back from `connection_config` after the `AUTH` webhook, writes it to `externalTenantId`. No DocuBite-side picker UI needed for Xero (Sage's `GET /businesses` pick still needs one, since Sage has no `connection_config` equivalent).
- **Token revoked mid-drain**: the in-flight proxy call 401s; `IntegrationAuthError` catch flips the row to `needs_reconnect` synchronously (the webhook will also fire and is idempotent with this). The push in hand fails this attempt (forced terminal, matching today's behaviour for an auth failure caught synchronously — the *next* queued push for the same connection hits the new pre-check and pauses without burning an attempt).
- **Same Xero org connected to two different Companies**: allowed — `@@unique([workspaceId, provider])` is per-workspace, not per external tenant, so nothing in the schema prevents it and nothing should; Nango's `connectionId` is minted per DocuBite connect session (one per workspace), so two workspaces get two independent Nango connections against the same Xero org. No dedupe needed or wanted (two DocuBite companies legitimately sharing a bookkeeper's org is a real case, not an error).
- **Disconnect while a post is queued**: disconnect deletes the `IntegrationConnection` row (Nango side + local). Per the `onDelete` change above, the queued `IntegrationPush` row keeps its `connectionId` as a plain (now-dangling, nullable) foreign key rather than cascading away — it is picked up by the claim loop, fails `connection` lookup (join returns null), and is force-terminaled with a new `errorCode: "integration_connection_removed"`, surfaced on the row exactly like any other terminal failure. Disconnect never un-posts what already succeeded (unchanged).

## Consequences

- `lib/integration-token-refresh.ts`, `lib/secret-crypto`'s use for this purpose, and the encrypted-column migration all retire; `lib/integrations/errors.ts`'s `IntegrationAuthError` stays (still thrown, now off a Nango proxy 401 rather than a refresh failure).
- The `IntegrationPush` → `IntegrationConnection` and `LedgerTransaction` → `IntegrationConnection` relations change `onDelete` behaviour — an additive-looking but behaviour-changing migration; call it out explicitly in the build ticket's migration review.
- Every provider client's `apiRequest` signature changes (token argument replaced by `connectionId`), touching `lib/integrations/quickbooks/client.ts`, `lib/integrations/xero/client.ts`, and the not-yet-written Sage client.

## Ordered build steps (inherited by the Nango-backed connections build)

1. **Schema**: migrate `IntegrationConnection` (drop token/expiry/scope columns, add `providerConfigKey`; status enum values `connected`/`needs_reconnect`; `onDelete: SetNull` + nullable `connectionId` on `IntegrationPush` and `LedgerTransaction`); delete existing rows. `kind: backend`.
2. **Nango client**: `lib/nango.ts` — session-mint call, `nangoProxy()` helper, webhook HMAC verify. `kind: backend`.
3. **Webhook route**: `app/api/webhooks/nango/route.ts` handling `AUTH` creation/refresh, connected/needs_reconnect flips, Owner email trigger. `kind: backend`.
4. **Connect-session route + retire old routes**: `app/api/integrations/connect-session/route.ts`; delete the four QuickBooks/Xero connect/callback route files. `kind: backend`.
5. **Provider clients**: rewrite `quickbooks`/`xero` `apiRequest` onto `nangoProxy`; write the Sage client per #378's endpoint list. `kind: backend`.
6. **Push loop**: `attemptIntegrationPush`'s pre-check (pause without burning an attempt on `needs_reconnect`), `getActiveIntegrationConnectionId`/`getLedgerConnectionBandStatus` status-string updates. `kind: backend`.
7. **Connect UI** (this is #383's build, not this ADR's — listed for sequencing only): the Accounting page's connect flow, org/business picker for Xero/Sage, reconnect band and Owner-email copy. `kind: surface`.
