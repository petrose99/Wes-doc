# Where competitors get "goods received" for a 3-way match on QBO and Xero

Research for issue #472 (feeds ADR 0019, #453). The question: QuickBooks Online and Xero appear to have no goods-received object, so how do Ramp, Zahara, Vic.ai and a few other SMB AP tools get the "goods received" leg of a 3-way match? Facts only, researched 2026-09-25.

**Labels.** **Confirmed** means read on the vendor's or provider's own page (help centre, API reference, OpenAPI spec, official SDK schema) in this pass. **Unverified** means it comes from a search-engine summary, a marketing page making a general claim, or inference. **Not found** means the question was looked for in primary sources and no answer was found; it is not filled from memory.

## Summary

**On QBO and Xero, every tool that offers a real receipt-based 3-way match holds receiving itself.** Ramp (Ramp-native item receipts), Zahara (GRNs in web and mobile app), Procurify, Lightyear and ApprovalMax all record receipts in their own product. None of them reads a goods receipt from QBO or Xero. Ramp says so outright for QBO: "You cannot 3-way match with imported POs from QBO, you will need to do everything in Ramp." Zahara says it does not pass GRN data to the ledger at all. ApprovalMax records only a header-level status (Not / Partially / Fully Received). Ramp reads receipts from the ERP only for NetSuite (and Sage Intacct). Vic.ai takes `quantityReceived` on each PO line through its API, pushed by whatever integration feeds it. Vic.ai's public material names only enterprise ERPs, and nothing found shows 3-way match on QBO or Xero.

**Ledger facts, with one correction.** Xero: confirmed. The PurchaseOrder schema has statuses DRAFT/SUBMITTED/AUTHORISED/BILLED/DELETED and no received quantity. Xero's own "part receive" (June 2026) works by part-billing, so "received" there means billed. QBO: **the premise needs updating.** The Accounting API still has no ItemReceipt entity in Intuit's official SDK schemas (last schema update 2026-07-17). But QBO **launched Item Receipts in the product UI** (help article updated 2026-08-05), and the shared schema has a read-only `Line.Received` on purchase-order lines. Whether the new UI item receipts can be read through the API was **not found**: Intuit's API reference pages are JS-rendered and could not be read.

## Ledger facts

### Xero: no received quantity. Confirmed.

- Xero's `PurchaseOrder` schema in the official OpenAPI spec (`XeroAPI/Xero-OpenAPI`, `xero_accounting.yaml`, last commit 2026-09-03, v19.0.0) has `Status` enum **DRAFT, SUBMITTED, AUTHORISED, BILLED, DELETED**. The delivery fields are only `DeliveryDate` ("Date the goods are to be delivered"), `DeliveryAddress`, `AttentionTo`, `Telephone`, `DeliveryInstructions` and `ExpectedArrivalDate`. PO lines use the shared `LineItem` schema (`Quantity`, `UnitAmount`, `AccountCode`, …), which has no received or billed quantity. Endpoints are `/PurchaseOrders`, `/{id}`, `/{number}`, `/History`, `/Attachments` and `/pdf`, with no receipt endpoint. Source: [xero_accounting.yaml](https://github.com/XeroAPI/Xero-OpenAPI/blob/master/xero_accounting.yaml) (read in full; the human docs page [developer.xero.com/documentation/api/accounting/purchaseorders](https://developer.xero.com/documentation/api/accounting/purchaseorders) is JS-rendered and returned no content to the fetcher).
- **Xero "part receive" is part-billing. Confirmed.** A Xero community manager, 2026-06-17: "being able to part receive items from your Purchase order has now been released to 100% of users". It works by creating bills from an approved PO with edited quantities; the PO shows a "Billed" column and auto-marks as billed when complete. Source: [Xero product ideas: Purchase Orders – Option to part-receive](https://productideas.xero.com/forums/967139-purchase-orders-bills-inventory/suggestions/47086402-purchase-orders-option-to-part-receive). No billed-quantity field appears in the OpenAPI spec, so whether it is visible through the API is **not found**.
- **Xero Inventory Plus** (the separate inventory product) has PO receiving, but it is **US-only** and an add-on to the Growing/Established plans, launched 2024-08-15 ([Xero media release](https://www.xero.com/us/media-releases/xero-unveils-inventory-software-xero-inventory-plus/)). Its receiving help article ([Receive a purchase order in Xero Inventory Plus](https://central.xero.com/s/article/Receive-a-purchase-order-in-Xero-Inventory-Plus)) could not be read (JS-rendered). No API for it was found.
- ApprovalMax corroborates the gap: "Unfortunately, the Xero API doesn't provide this option. That's why we use allocations instead of matching Line Items." ([ApprovalMax](https://support.approvalmax.com/en/articles/414117-bill-to-po-matching-is-it-possible-to-match-line-items-xero)).

### QuickBooks Online: no ItemReceipt API entity, but a new UI item receipt. Partly confirmed, partly not found.

- **No ItemReceipt entity in the API schema. Confirmed (SDK).** Intuit's official Java SDK schema (`ipp-v3-java-data/src/main/xsd`, last schema commit 2026-07-17 "Add V3 Schema Updates") declares 70 `IntuitObject` entities, including `PurchaseOrder`, `Bill`, `Purchase`, `VendorCredit` and `InventoryAdjustment`. **`ItemReceipt` is not one of them.** `ItemReceipt` appears only as a `TxnTypeEnum` value and as `ItemReceiptLineDetail` (a line-detail type whose body is an "Internal use only" extension placeholder). No `ItemReceipt` data class exists in either the Java or the .NET SDK. Sources: [IntuitRestServiceDef.xsd](https://github.com/intuit/QuickBooks-V3-Java-SDK/blob/develop/ipp-v3-java-data/src/main/xsd/IntuitRestServiceDef.xsd), [Finance.xsd](https://github.com/intuit/QuickBooks-V3-Java-SDK/blob/develop/ipp-v3-java-data/src/main/xsd/Finance.xsd). This schema is shared with Desktop-era types (it also has `SalesOrder`, `ChangeOrder`), so its entity list is an upper bound on QBO, not an exact list. The .NET SDK's `IdsResource` enum lists `itemreceipt`, but that enum also carries legacy QBD resources (`payrollitem`, `uom`, `salesorder`), so it is not evidence of a QBO endpoint.
- **PO status and received. Confirmed (SDK).** `PurchaseOrderStatusEnum` is **Open, Closed**. The shared `Line` type has `Received` ("The amount/quantity received of the line… ReadOnly field for Purchase Order."). Source: Finance.xsd above. What populates it in QBO (bills linked to the PO, or the new item receipts) is **not found**.
- **ItemReceipt is a QuickBooks Desktop API object. Confirmed.** The Desktop SDK reference has ItemReceiptAdd, ItemReceiptMod and ItemReceiptQuery ([ItemReceiptAdd](https://developer.intuit.com/app/developer/qbdesktop/docs/api-reference/qbdesktop/itemreceiptadd), listed in Intuit's [docs sitemap](https://developer.intuit.com/docs_sitemap.xml)).
- **QBO now has Item Receipts in the UI. Confirmed. This changes the premise.** Intuit help article, updated 2026-08-05, applies to Ledger, Simple Start, Essentials, Plus, Advanced and Solopreneur. It is enabled by "Settings → Account and settings → Sales → Inventory receiving method → Item receipts", and "they can't be turned off". It is created from "All apps → Inventory → Item receipts", either by adding a PO or manually. It supports partial deliveries, and a bill links "a Purchase Order or an Item receipt". It increases Inventory Asset and AP, and "The Cost of Goods Sold will come from the Item Receipt, even if there's a linked Bill." Source: [Receive inventory with an Item receipt](https://quickbooks.intuit.com/learn-support/en-us/help-article/inventory-account/receive-inventory-item-receipt/L5xIhKRpV_US_en_US).
- **API exposure of the new item receipts: not found.** The QBO API reference ([purchaseorder](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/purchaseorder)) and the [release notes](https://developer.intuit.com/app/developer/qbo/docs/release-notes/platform-release-notes) are JS-rendered and could not be read. A request for `/all-entities/itemreceipt` returns the SPA shell (HTTP 200 for any path, so this proves nothing). **Test in a sandbox**: query `select * from ItemReceipt`, and read `Bill.LinkedTxn` for a bill linked to a UI item receipt.
- **Without item receipts, QBO receives by billing. Confirmed.** "After a vendor accepts a purchase order and sends the products, record it as a bill or expense"; partial receipt is done by adding part of the PO to a bill, expense or check; "QuickBooks Online automatically closes purchase orders when all quantities are added to bills, expenses, or checks." ([Add purchase orders to expenses, bills, or checks](https://quickbooks.intuit.com/learn-support/en-us/help-article/purchase-orders/add-purchase-orders-expenses-bills-checks-online/L9pRK49uC_US_en_US)).

## Ramp

1. **Where receiving is held. Confirmed.** "You can create Item Receipts directly in Ramp to mark a PO as received. You do not need to have a direct ERP integration to do this." "Users with permission to manage purchase order receipts can create item receipts." Receipts are imported from NetSuite and Sage Intacct: "New item receipts are imported daily". For QBO: "You cannot 3-way match with imported POs from QBO, you will need to do everything in Ramp." Xero is not mentioned. Mobile receiving: not found. Source: [3-Way Match with Ramp Procurement](https://support.ramp.com/3-way-match-with-ramp-procurement). On the Bill Pay PO-import page, PO import is "supported for NetSuite, Sage Intacct, and QuickBooks Online" (plus CSV), and item-receipt matching is described only for NetSuite ([Importing and matching POs](https://support.ramp.com/importing-and-matching-purchase-orders-pos-on-ramp-bill-pay)). Ramp's blog: open a PO "and simply press 'R' to immediately generate an item receipt" ([Ramp blog](https://ramp.com/blog/three-way-match-ai-and-more-procurement-upgrades)).
2. **The match. Confirmed.** Per line. "You can only configure the quantity for Inventory line items… Otherwise, the line item type will be treated as an Expense line item which can only be marked as Received or Not Received." Mismatch **warns**: "We'll show an alert if the billed units haven't been received"; when matched: "All billed units have been received". (3-way article above.) Overbilling Protection is separate. It compares bills with the **PO**, not the receipt. It has header tolerances (% of PO total and/or fixed amount; "whichever limit is hit first") and line tolerances on rate and quantity. Within tolerance it warns ("Line item quantity exceeds PO but within threshold"); beyond it, it errors, and a header breach blocks bill creation ([Overbilling Protection](https://support.ramp.com/overbilling-protection/)). None of the tolerance settings found involves received quantity.
3. **Who it's sold to. Confirmed.** Ramp-native 3-way needs "the Procurement add-on"; PO import needs Ramp Plus. Pricing: Plus is "$15/mo/user + Platform fee"; Procurement is an "Add-on to Plus or Enterprise", which includes "Three-way match with Ramp purchase orders and item receipts" ([Ramp pricing](https://ramp.com/pricing)). Evidence of small QBO companies actually using 3-way: **not found** beyond the help-centre instruction for QBO users above.

## Zahara

1. **Where receiving is held. Confirmed.** Zahara's own GRN. From the PO list, "click the GRN icon"; a wizard asks if the order is received in full, and "You can adjust any received quantities", set the delivery date, add a GRN number and upload the GRN document ([Understanding GRN's](https://ask.zaharasoftware.com/understanbding-grns), updated 2025-05-12). "Receipting is simply specifying a quantity received per line item." Decimals and negatives are allowed, a negative GRN undoes a delivery, and "Zahara isn't a stock system and we don't pass GRN data into the finance system but it is possible." ([Receipt a Delivery](https://ask.zaharasoftware.com/receipt-a-delivery), 2025-05-15). On mobile (Zahara Go, 2025): per-line checkbox or "Fully Receive All", adjustable quantities, and a photo of the delivery note attached; "We don't offer the scanning of delivery notes and intelligent reading" ([Zahara Go](https://ask.zaharasoftware.com/zahara-go), 2025-07-31). The ledger integrations send only bills: for Xero, "it is just the purchase invoice we hand over to Xero" ([Xero integration explained](https://ask.zaharasoftware.com/xero-integration-explained)); for QBO it syncs vendors, GL codes, tax rates and classes and exports bills/expenses ([Understanding QuickBooks Online](https://ask.zaharasoftware.com/quickbooks-online-integration-overview)). (These help articles were read through the help site's JSON endpoint, `/api/articles/article/<slug>`, because the pages render client-side.)
2. **The match. Confirmed.** GRN status per order is Green (fully received), Orange (not fully received) or Red (over-receipted). In the invoice settings, "you can warn the invoice creator that the order hasn't been fully receipted. You can even prevent the order from being raised." There is an optional "Prevent additional GRNs" once fully delivered, and an "Order adjustment to GRN" setting that shrinks the PO to what was delivered ([GRN Controls & Settings](https://ask.zaharasoftware.com/grn-controls-settings)). The "Check for GRN" invoice-workflow step **holds** the invoice until the chosen condition holds: "Fully Received" or "Partially Received", with partial fixed at 50%, or a configurable "GRN %". It sends recurring reminders meanwhile ([Waiting for a GRN Workflow Step](https://ask.zaharasoftware.com/waiting-for-a-grn-workflow-step)). Line-by-line invoice-to-PO matching (manual or AI; one-to-many and many-to-many) is a **beta**, opt-in per business ([AI Line By Line Matching](https://ask.zaharasoftware.com/line-by-line-matching), 2026-01-21). Numeric price tolerances: **not found** in the help articles read. The marketing page says an invoice "is placed on hold until it is investigated" ([3-way matching page](https://www.zaharasoftware.com/accounts-payable/3-way-matching-in-accounts-payable)).
3. **Who it's sold to. Confirmed.** Teams £159/mo, Business £289/mo, Enterprise £499/mo, Enterprise+ custom. The page does not say which plan includes GRN ([pricing](https://www.zaharasoftware.com/pricing)). "Trusted by 500+ teams" ([Xero page](https://www.zaharasoftware.com/zahara-erp-and-finance-integrations/accounts-payable-automation-for-xero)). Named Xero and QBO customers using GRN: not found.

## Vic.ai

1. **Where receiving is held. Confirmed (API).** Vic.ai does not record receipts. The public API's PO line item has `matchingType` (`two_way`, `three_way` default, `four_way`). `three_way` requires `quantityRequested` and `quantityReceived`; `four_way` adds `quantityAccepted`. The integration must "supply and update" master data, including POs ([vic.api.v0.yaml](https://github.com/Vic-ai/api-docs/blob/HEAD/vic.api.v0.yaml), [API intro](https://github.com/Vic-ai/api-docs/blob/HEAD/docs/main.md); repo last pushed 2024-09-16). So receipts come from whatever system feeds Vic.ai. For QBO or Xero, which have no receipt quantity in their APIs (see above), there is no ledger source for `quantityReceived`; how Vic.ai handles that is **not found**.
2. **The match. Confirmed (data sheet).** "2-, 3-, and 4-way PO matching at the line-item level", "Set tolerance levels for price, quantity, and other criteria", mismatches "flagged for human review" via "customizable mismatch approval flows" ([PO Matching data sheet PDF](https://4808453.fs1.hubspotusercontent-na1.net/hubfs/4808453/One%20Pagers/Vic.ai%20Autonomous%20PO%20Matching%20Overview.pdf)). AutoPost fires only when all lines are "exact or within tolerance of your PO Mismatch flows" ([Autopilot help](https://intercom.help/vicai/en/articles/5071874-autopilot), updated 2025-12-04). So a mismatch routes to an approval flow rather than posting.
3. **Who it's sold to.** The integrations pages list Oracle, Microsoft, Coupa, Sage, Workday and Vista, with **no QBO or Xero** ([erp-integrations](https://www.vic.ai/erp-integrations), [integrations](https://vic.ai/integrations)). The data sheet names Oracle, SAP and Microsoft Dynamics. A 2023 help article covers connecting QBO clients, but it describes only authentication and AI training on history, with no PO or receipt sync ([QBO sync](https://intercom.help/vicai/en/articles/3622365-how-to-sync-your-quickbooks-online-client-with-vic-ai)). No public pricing ([pricing](https://www.vic.ai/pricing)). **Unverified:** that Vic.ai 3-way works for any QBO or Xero customer.

## Others (brief)

- **ApprovalMax. Confirmed.** GRN is a PO-level status (Not / Partially / Fully Received), available only once the PO is fully approved. The requester, approvers or admins set it, with comments and attachments, and it can be pushed to Xero History. Advanced and Premium plans only, on both Xero ([GRN](https://support.approvalmax.com/en/articles/413360-goods-received-note-grn), 2025-11-06) and QBO ([GRN for QBO](https://support.approvalmax.com/portal/en/kb/articles/does-approvalmax-support-goods-received-note-for-quickbooks-online-po)). Bill-to-PO matching allocates amounts and has % tolerances, and can block approval of unmatched bills ([Advanced settings](https://support.approvalmax.com/en/articles/414114-advanced-settings-for-bill-to-purchase-order-matching), 2025-10-29). The Advanced and Premium plans are required on Xero, and Xero Standard lost matching on 1 April 2023 ([plans](https://support.approvalmax.com/en/articles/414119-xero-in-which-plans-is-bill-to-po-matching-available)). Using GRN status as a bill-approval condition: **not found**.
- **Dext. Confirmed.** PO Match links a cost item to an open Xero (Draft/Approved) or QBO (Open) PO. "If the item total doesn't fully match the purchase order total, a warning appears… You can still continue". There is no receipt leg ([Using Purchase Order Match](https://help.dext.com/en/articles/416706-using-purchase-order-match), 2026-08-24).
- **Lightyear. Confirmed, but from blog posts.** "Capture and mark when goods/services have been delivered… line by line. Attach proof of works or proof of delivery to the appropriate Goods Received Record" ([PO launch post](https://www.lightyear.cloud/company-blog/introducing-purchase-orders-with-3-way-matching/)). Later: "Lightyear now automates the matching of all your Purchase Orders to Goods Received Notes to Supplier Bills on the line-item level" ([Q2 2021](https://www.lightyear.cloud/company-blog/feature-release-q2-2021/)). The Xero partner page lists 3-way matching ([Xero](https://www.lightyear.cloud/partners/software-partners/xero)). Tolerances and mismatch behaviour: not found.
- **Procurify. Confirmed in part.** Receiving is done in Procurify (web and mobile, "Snap a picture of the packing slip", per-line "passed"/"failed") ([receiving](https://www.procurify.com/procure-to-pay/procurement/receiving-inventory/)). Automated 3-way checks "variances in unit cost and received quantity" ([Automated 3-Way Matching](https://success.procurify.com/en/articles/10054484-automated-3-way-matching), 2024-10-29). The QBO integration syncs vendors, account codes and bills, and "QuickBooks inventory does not sync" ([QBO FAQ](https://success.procurify.com/en/articles/9001975-quickbooks-online-integration-overview-faq), 2026-06-03). Whether POs or receipts sync to QBO is not stated. Xero is not in the integration list (unverified; a search-result claim, not read on a Procurify page).
