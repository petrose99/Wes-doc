# Changing the expense account on an already-posted bill — QBO, Xero, Sage

Research for: when a supplier bill (or a receipt posted as an expense) went to the ledger with the wrong expense account, can DocuBite fix the account on the posted document through the provider API, and when will the provider refuse? Facts only, researched 2026-09-24.

**Labels.** **Confirmed** means read on the provider's own page, or in the provider's API help, in this pass. **Confirmed (mirror)** means read in an SDK generated from the provider's OpenAPI spec, because the provider's page itself blocked automated fetches. **Unverified** means it comes from a search-engine summary, a third-party help centre or inference. Treat unverified items as hypotheses to test in a sandbox.

## Summary

All three providers let an app change a line's account on a document it has already posted, but each has its own refusal rules. **Xero** is the most permissive and the best documented. `POST /Invoices/{InvoiceID}` can change `AccountCode` on an AUTHORISED bill, and also on a part-paid or fully PAID bill, because line `AccountCode` is on Xero's list of fields that stay editable after payment. Xero refuses a bill in a locked period, a bill that is VOIDED or DELETED, and a change to a CIS account code. Line items missing from the request are deleted, so every line has to be sent back with its `LineItemID`. **QuickBooks Online** has only a *full* update for Bill and Purchase (the docs list no sparse update for either). The request must carry the current `SyncToken` and every writable field; any writable field left out is set to NULL. QBO refuses with **6200 / 6210 "Account Period Closed"** when the transaction falls on or before the books-closing date, and an app can predict this by reading `Preferences.AccountingInfoPrefs.BookCloseDate`. **Sage** has a caveat that matters more than any single rule: **South African Sage Business Cloud Accounting runs on a different platform from the v3.1 API at developer.sage.com** (unverified, but consistent with everything else found). ZA companies use the Sage One SA API v2.0.0 (`accounting.sageone.co.za/api/2.0.0`), where a supplier invoice is re-saved through `POST SupplierInvoice/Save`. That API exposes read-only `Editable`, `Locked`, `Paid`, `Status` and `TaxPeriodId` flags on the invoice, and `LockProcessing`/`LockProcessingDate` on the company. In both Sage products the UI refuses to edit an invoice that is paid or allocated, sits on a submitted VAT return, or is dated before the lockdown date. **This repo pins Sage v3.1 (`lib/integrations/sage/config.ts`), so check whether v3.1 can reach a ZA business at all before building anything Sage-specific.** In every provider the document's ID stays the same through an update. Xero and QBO both write a history or audit entry, and none of the providers is documented to re-trigger payment workflows. Tax on the line follows the new account's default only if the request leaves out the explicit tax code (confirmed for Xero, unverified for the others).

## QuickBooks Online

1. **Call shape. Confirmed.** The Bill reference lists Create, Delete, Query, Read and **"Full update a bill"**, with no sparse-update section. The full-update text says: "The request body must include all writable fields of the existing object as returned in a read response. Writable fields omitted from the request body are set to NULL." `SyncToken` is described as "Version number of the object. It is used to lock an object for use by one app at a time… Attempts to modify an object specifying an older SyncToken fails." `Line` is required and takes `ItemBasedExpenseLine` or `AccountBasedExpenseLine`, with the account in `AccountBasedExpenseLineDetail.AccountRef`. The Purchase reference likewise lists only "Full update a purchase". Source: [Bill](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/bill), [Purchase](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/purchase). In practice: read the bill, change `AccountRef` on the target lines, and POST the whole object back, lines included.
2. **Refusals.**
   - **Closed period. Confirmed.** The error-code table lists "6200 Account Period Closed Error — The user has 'closed the books' so the account period is closed for edits" and "6210 … A password is required to make changes and updates" ([error codes](https://developer.intuit.com/app/developer/qbo/docs/develop/troubleshooting/error-codes)). Intuit's 6210 article: "The account period has closed and the account books cannot be updated through through the QBO Services API. Please use the QBO website to make these changes." It advises apps to read `Preferences → AccountingInfoPrefs.BookCloseDate` (minor version 21) and check the transaction date before sending ([6210 article](https://help.developer.intuit.com/s/article/6210-Account-Period-Closed)). `BookCloseDate` appears in the [Preferences](https://developer.intuit.com/app/developer/qbo/docs/api/accounting/all-entities/preferences) response.
   - **Stale object. Confirmed.** "5010 Stale Object — The requested update is for a stale object. Client needs to refresh the object." (error codes page).
   - **Paid or part-paid. Unverified.** Bill `Balance` "reflect[s] any payments made… A Balance of 0 indicates the bill is fully paid" and `LinkedTxn` can be `BillPaymentCheck` (confirmed). Nothing in the docs forbids an account change on a paid bill. The payment links on the bill side are system-maintained, and the linked-transactions page says BillPayment→Bill links are set "through the BillPayment.Line.LinkedTxn element" ([linked transactions](https://developer.intuit.com/app/developer/qbo/docs/workflows/manage-linked-transactions)). Whether a full update that changes only `AccountRef` and keeps the amounts leaves the payment attached is **unverified**; test it in the sandbox.
   - **Delete. Confirmed.** "You must unlink any linked transactions associated with the bill object before deleting it." (Bill page). 6220 "Delete Entity Has Balance Error".
   - **Voided bill, reconciled expense, filed tax return. Unverified.** Nothing documented was found.
3. **Side effects.** The `Id` stays the same (it is passed in the body); `SyncToken` increments (confirmed). `TxnTaxDetail` "can be calculated by QuickBooks business logic or you may supply it" (confirmed), but whether changing the account alone recalculates tax is unverified. Attachments are separate `Attachable` entities referencing the transaction ID, so they should survive an ID-preserving update (unverified). QBO's Audit Log records edits in the UI, but it has no documented API (unverified; the help page could not be fetched).
4. **Pre-check. Confirmed.** Read `BookCloseDate` once per connection, then `GET bill/{id}` for `SyncToken`, `TxnDate`, `Balance` and `LinkedTxn`.

## Xero

1. **Call shape. Confirmed.** `POST Invoices` is "Use this method to create or update an invoice". The line-item rules, quoted: "Providing an existing LineItem with its LineItemID will update that line item. Providing a LineItem with no LineItemID will create a new line item. Not providing an existing LineItem with it's LineItemID will result in that line item being deleted." And: "If LineItemIDs are not included… then the line items are deleted and recreated." ([Invoices](https://developer.xero.com/documentation/api/accounting/invoices)). BankTransactions uses the same wording, and `PUT BankTransactions` creates only ([BankTransactions](https://developer.xero.com/documentation/api/accounting/banktransactions)). In practice: send all lines with their IDs and change `AccountCode` on the target lines.
2. **Refusals. Confirmed** unless marked otherwise.
   - Updating Invoices table: ACCPAY is updatable when unpaid ("Yes") and when "Paid (in part, or in full) — Yes – with exceptions below", but not "In a locked period — No".
   - Fields editable on a part- or fully-paid ACCPAY: Reference, DueDate, InvoiceNumber, BrandingThemeID, Contact (unless paid with a credit note or the lines contain a CisLabourExpense account), Url, LineItems, Description, **AccountCode, except for Construction Industry Scheme (CIS) account codes**, Tracking, PlannedPaymentDate. **An account change on a paid bill is allowed.** Changing the amounts is not on the list.
   - Valid status transitions: DRAFT/SUBMITTED → DRAFT, SUBMITTED, AUTHORISED or DELETED; AUTHORISED → AUTHORISED or VOIDED. There are none from PAID, VOIDED or DELETED, and "If an invoice has been AUTHORISED it cannot be deleted but you can set it's status to VOIDED". So VOIDED and DELETED bills are final. Updating a VOIDED bill's lines is unverified but implied to be refused.
   - Lock dates: `GET Organisation` returns `PeriodLockDate` and `EndOfYearLockDate` ([Organisation](https://developer.xero.com/documentation/api/accounting/organisation)). The field error text "The document date cannot be before the end of year lock date, currently set at &lt;date&gt;" comes from third-party help centres such as [Dext](https://help.dext.com/en/articles/105721-the-document-date-cannot-be-before-the-end-of-year-lock-date-currently-set-at-date) (**unverified** on a Xero page). A Xero Developer Ideas thread says the API applies the lock "all or nothing", unlike the UI, which allows some fields ([Ideas](https://xero.uservoice.com/forums/5528-accounting-api/suggestions/39269707-ability-to-change-expectedpaymentdate-on-invoice-w); **unverified**, not read directly).
   - Error envelope: HTTP 400 `ValidationException`, or HTTP 200 with a per-item `StatusAttributeString: "ERROR"` and `ValidationErrors` when `summarizeErrors=false` ([requests and responses](https://developer.xero.com/documentation/api/accounting/requests-and-responses)).
   - Reconciled spend money (`IsReconciled`: true): whether an account-only change is refused is **unverified**.
3. **Side effects.** `TaxType` is "Used as an override if the default Tax Code for the selected AccountCode is not correct" (confirmed). Changing `AccountCode` without sending `TaxType` therefore picks up the new account's default tax, and sending the old `TaxType` keeps it. The `InvoiceID` stays the same (it is in the URL). Attachments hang off `Invoices/{id}/Attachments`, so they should survive (unverified, not stated). History: `GET Invoices/{id}/history` records the change, and the User is "System Generated" when the change happens via the API ([History and Notes](https://developer.xero.com/documentation/api/accounting/historyandnotes), confirmed). An app can also add a note with `PUT …/history`. For amounts on a SUBMITTED or AUTHORISED invoice, "totals are calculated from the line items" unless SubTotal, TotalTax and Total are all supplied (confirmed).
4. **Pre-check. Confirmed.** `GET Invoices/{id}` (`Status`, `AmountPaid`, `Payments`, `LineItems[].LineItemID`) plus `GET Organisation` (lock dates).

## Sage

### Which Sage API serves South Africa

- **Unverified, and the most important point.** A Sage-owned developer-community article, "Does the Sage Business Cloud Accounting API work for South Africa?", was seen only as a search snippet because Cloudflare blocked the fetch. It says the ZA product "is based on an entirely different codebase and technology to the product of which the APIs on developer.sage.com is based", and that ZA has its own API documented on the South African site ([article](https://developer-community.sage.com/articles.html/supporting-you/does-the-sage-business-cloud-accounting-api-work-for-south-africa-r6/)). Search summaries of Sage's migration guide list v3.1 countries as UK, IE, US, CA, FR, ES and DE, with no ZA ([migrate v1→v3.1](https://developer.sage.com/accounting/guides/migrating/migrate-from-v1-to-v3-1/), also blocked).
- **Corroborated.** The ZA knowledge base describes a different UI ("Suppliers → Transactions → Supplier Invoices", line types Item/Account/Time/Bundle) ([za-kb processing supplier invoices](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=200124134426929)). The ZA API help is live at [accounting.sageone.co.za/api/2.0.0/Help](https://accounting.sageone.co.za/api/2.0.0/Help) (confirmed, fetched).
- **Impact on this repo.** `lib/integrations/sage/config.ts` pins `https://api.accounting.sage.com/v3.1` through Nango. If DocuBite's Sage customers are ZA businesses, the v3.1 rules below may not apply to them. Checking this belongs to the Sage integration work, not to this note.

### Sage ZA (Sage One SA API v2.0.0). Confirmed from the API help unless marked

1. **Call shape.** `POST SupplierInvoice/Save?useSystemDocumentNumber=` ("Saves the specified Supplier Invoice"). The body has `ID`, `Lines` (a collection of Commercial Document Line) and more. Each line has `ID`, `SelectionId` ("the selected Item Id or Account Id"), `LineType`, `TaxTypeId` and `Quantity` ("For a LineType of Accounts, a Quantity of 1 is required") ([Save](https://accounting.sageone.co.za/api/2.0.0/Help/Api/POST-SupplierInvoice-Save_useSystemDocumentNumber), [line model](https://accounting.sageone.co.za/api/2.0.0/Help/ResourceModel?modelName=CommercialDocumentLine)). Two points are **unverified**: that Save with an existing `ID` updates the invoice, and that the whole line set must be resent. The body is the full document, so plan to send it all. Expenses go through `POST BankTransaction/Save`, whose body carries `SelectionId`, `TaxTypeId`, `Reconciled`, `Accepted` and a read-only `Editable`, `Locked` and `HasAllocations` ([BankTransaction Save](https://accounting.sageone.co.za/api/2.0.0/Help/Api/POST-BankTransaction-Save)).
2. **Refusals.**
   - **Read-only flags.** The invoice exposes `Editable`, `Locked`, `Paid` ("This field is not editable"), `Status` and `TaxPeriodId`. The company exposes `LockProcessing` and `LockProcessingDate` ([Company/Current](https://accounting.sageone.co.za/api/2.0.0/Help/Api/GET-Company-Current)). Tax periods expose `Status` and `SubmissionDate` ([TaxPeriod/Get](https://accounting.sageone.co.za/api/2.0.0/Help/Api/GET-TaxPeriod-Get)). The API's own error text for a refused Save was not found (**unverified**).
   - **Lockdown date.** "Setting a Lockdown Date means that you can not process or edit any transactions before this date… all transactions processed before this date will become view only." ([za-kb lockdown date](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=250213110439240), confirmed UI rule).
   - **VAT period.** "For transactional changes you'll need to reopen the VAT Period, process amendments to transactions, close the VAT Period again and re-initiate the VAT 201 Wizard", and "SARS won't allow you to resubmit any VAT 201 report that you've previously submitted" ([za-kb VAT 201 FAQ](https://za-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=210701103812810&view=print), confirmed UI rule). The API can open and close tax periods (`POST TaxPeriod/OpenTaxPeriod` and `CloseTaxPeriod` are listed), but DocuBite should not do that on the bookkeeper's behalf.
   - **Paid or allocated.** Unverified for ZA. The UK rule below probably applies. The API exposes `Allocation/Delete` and `Allocation/Save`.
3. **Side effects.** `HasAttachments` is on the invoice, and attachments live in `SupplierInvoiceAttachment/*` keyed by the invoice, so an update with the same `ID` should keep them (unverified). An audit trail is available through `GET DocumentHistory/Get?documentHeaderId=&documentTypeId=` (the endpoint is confirmed to exist; that it records API edits is unverified). Tax follows the line's `TaxTypeId`, which DocuBite sends explicitly.
4. **Pre-check.** `GET SupplierInvoice/Get/{id}` (`Editable`, `Locked`, `Paid`, `AmountDue`, `TaxPeriodId`) plus `GET Company/Current` (`LockProcessingDate`). `Editable` is the cheapest single predictor, though what it covers is not documented.

### Sage v3.1 (developer.sage.com; mirror = SynergiTech/sage-php, generated from Sage's OpenAPI)

1. **Call shape. Confirmed (mirror).** `PUT /purchase_invoices/{key}` "Updates a Purchase Invoice". The PUT line schema (`ledger_account_id`, `tax_rate_id`, `net_amount`, `tax_amount`…) has **no line `id`**. A third-party summary says "The 'Update Invoice' PUT action will overwrite any invoice line items" (**unverified**, [cleverence](https://www.cleverence.com/articles/sage-documentation/sage-accounting-api-purchase-transactions-3-1-7394/)), so resend all lines. `tax_amount` "is required in v3.1, unless the tax rate is of a 'zero', 'exempt' or 'no_tax' type" (mirror). Expenses: `PUT /other_payments/{key}`, which exposes `editable` and `deletable`. Source: [PurchaseInvoicesApi](https://github.com/SynergiTech/sage-php/blob/HEAD/docs/Api/PurchaseInvoicesApi.md), [PurchaseInvoice model](https://github.com/SynergiTech/sage-php/blob/HEAD/docs/Model/PurchaseInvoice.md), [PUT line model](https://github.com/SynergiTech/sage-php/blob/HEAD/docs/Model/PutPurchaseInvoicesPurchaseInvoiceInvoiceLinesInner.md). developer.sage.com itself returned a Cloudflare challenge on every fetch.
2. **Refusals.** From the UK help centre: "You can only edit an invoice if… The invoice is unpaid; The invoice has no allocations; The invoice isn't on a VAT Return". A draft VAT return must be deleted first; for a submitted one, "you can't edit the invoice. Instead, reverse the purchase invoice" ([gb-kb Edit a purchase invoice](https://gb-kb.sage.com/portal/app/portlets/results/view2.jsp?k2dockey=222001000101078), confirmed UI rule; that the API enforces the same is unverified). The UK KB also says "Once you include a transaction on a VAT Return, you can't delete or edit it" and to correct by reversing ([gb-kb Correct transactions on a VAT Return](https://gb-kb.sage.com/portal/app/portlets/results/view2.jsp?k2dockey=222001000101228)). Lockdown: `financial_settings.year_end_lockdown_date` exists (mirror), and the UK edit wizard says to check that no lockdown date is set first ([gb-kb](https://gb-kb.sage.com/portal/app/portlets/results/viewsolution.jsp?solutionid=240124182115040&hypermediatext=null)). Error text: not found.
3. **Pre-check. Confirmed (mirror).** `purchase_invoices/{key}` returns `editable` ("Indicates whether artefact can be edited"), `status`, `outstanding_amount`, `void_reason` and `tax_reconciled`, plus `deleted_at`.
