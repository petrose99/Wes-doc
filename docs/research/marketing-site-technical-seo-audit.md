# Marketing site technical SEO audit

Ticket: [#129 — Technical SEO gap list](https://github.com/petrose99/docubite/issues/129) (Map #126: Multi-page marketing site redesign + SEO)

This is a local code audit of `app/(marketing)/` and the root layout as they exist on `master` — not a live Lighthouse/PageSpeed run and not general web research. Structured data and Core Web Vitals threshold claims are cited to schema.org and web.dev; everything else is a direct read of the files named below. This is a planning document: it specifies gaps and how to close them, but implements nothing.

## Method and limitations

Read directly: `app/layout.tsx`, `app/(marketing)/layout.tsx`, `app/(marketing)/page.tsx`, `app/(marketing)/pricing/page.tsx`, `app/(marketing)/solutions/page.tsx`, `app/(marketing)/solutions/[slug]/page.tsx`, `app/(marketing)/demo/page.tsx`, `lib/config.ts`, `lib/solutions.ts`, and all 18 homepage section components under `components/marketing/landing/`. Searched the whole repo (`app/`, `components/`, `lib/`, `public/`) for `sitemap`, `robots`, `application/ld+json`, `schema.org`, `canonical`, `next/image`, and `<img`. Two WebFetch calls: schema.org's `SoftwareApplication` type page, and web.dev's Core Web Vitals article — used only to source the "why it matters" framing in the gap list, not to audit DocuBite itself.

Not covered here (out of scope for a static code read): actual rendered Lighthouse/PSI scores, real network waterfall, or crawl-budget behavior — those require a live audit against a deployed URL, which the ticket explicitly excludes.

## Current state

What's already in place, so it doesn't get re-flagged as a gap:

- **Title templating** — `app/layout.tsx` sets `metadata.title = { template: "%s | DocuBite", default: "DocuBite" }`, and both `app/(marketing)/page.tsx` and `pricing/page.tsx` opt out of the template with `title: { absolute: "..." }` for standalone titles. `solutions/page.tsx` and `demo/page.tsx` use the templated form (`title: "Solutions"` → renders "Solutions | DocuBite").
- **Per-page descriptions** — every marketing route (`page.tsx`, `pricing/page.tsx`, `solutions/page.tsx`, `demo/page.tsx`) exports a unique, page-specific `description` string. None are missing or duplicated.
- **Dynamic per-solution metadata** — `app/(marketing)/solutions/[slug]/page.tsx` has `generateMetadata()` pulling `title`/`description` from `lib/solutions.ts` per slug (11 solutions in `SOLUTIONS`), plus `generateStaticParams()` so all 11 slugs are pre-rendered at build time, not left to on-demand ISR.
- **metadataBase** — `app/layout.tsx` sets `metadataBase: new URL(config.app.baseURL)`, so any relative OG/twitter image paths would resolve correctly once added.
- **OpenGraph and Twitter card scaffolding** — `app/layout.tsx` sets `openGraph: { type, locale, url, title, description, siteName }` and `twitter: { card: "summary_large_image", title, description }` at the root, inherited by every marketing page that doesn't override them.
- **robots meta tag** — `app/layout.tsx` sets `robots: { index: true, follow: true }` globally; nothing is accidentally set to noindex.
- **Favicon/manifest/theme-color** — icons, `apple-touch-icon.png`, `site.webmanifest`, and a `viewport.themeColor` are all wired in `app/layout.tsx`.
- **Font loading** — `Inter` is self-hosted via `next/font/local` (not a Google Fonts network hop) and `Bricolage_Grotesque` via `next/font/google`, both with `display: "swap"` — no FOIT, and self-hosting Inter avoids an extra third-party connection that would otherwise cost LCP/CLS.
- **No `<img>` tags anywhere in marketing routes or homepage sections** — every homepage section (`components/marketing/landing/*.tsx`) is built from CSS/SVG/markup mockups, not raster images, per repo grep. This means there's currently no unoptimized-image risk to fix, but also no `next/image` usage to point to as an established pattern once real screenshots/photos are added.
- **Single, correct H1 per page** — verified: homepage H1 lives only in `components/marketing/landing/hero.tsx` (one `<h1>`); `pricing`, `solutions`, `solutions/[slug]`, and `demo` each have exactly one `<h1>` in their own `page.tsx`. No page has zero or multiple H1s. (The unused `components/marketing/sections/hero.tsx` and `components/marketing/prototype/landing-page-prototype.tsx` also define `<h1>`s, but per `app/(marketing)/page.tsx` these are dead/prototype-only code paths — the prototype only renders behind `NODE_ENV !== "production"` and a `?variant=` query param — so they don't create a live duplicate-H1 problem today. Worth remembering if the prototype variant is ever promoted to production.)
- **Sane heading hierarchy on the homepage** — the 18 sections stacked in `app/(marketing)/page.tsx` each use `<h2>` for their section headline (verified via grep count across `components/marketing/landing/*.tsx`); no section skips to `<h3>` without an `<h2>` parent. `Hero`, `Proof`, and `ReadsStrip` have no heading of their own (visual-only or strip components), which is fine — they aren't skipping a level, they simply don't need one.
- **FAQ content already exists in a good shape to become FAQPage structured data** — `components/marketing/landing/faq.tsx` has 7 question/answer pairs in a `QUESTIONS` array rendered as `<details>/<summary>`, i.e. already question-and-answer-shaped data ready to mirror into JSON-LD without new copywriting.

## Gap list

Ordered most-impactful first.

1. **No `robots.txt` route at all.** Neither `app/robots.ts` (Next.js App Router convention) nor `public/robots.txt` exists anywhere in the repo. Without one, crawlers fall back to default behavior (crawl everything, including any accidentally-exposed internal routes like `/admin-next` or API routes under `app/api/`), and there's no `Sitemap:` directive pointing crawlers at a sitemap even once one exists. **Why it matters:** `robots.txt` is the first file crawlers check and is the standard mechanism for declaring which paths are crawlable and where the sitemap lives (per Google's own crawler documentation and the robots.txt spec that `next/robots` implements). **How to close:** add `app/robots.ts` exporting a `MetadataRoute.Robots` object — allow `/`, `/pricing`, `/solutions`, `/solutions/*`, `/demo`; disallow `/admin-next`, `/api`, `/workspaces`, `/login`, `/signup` (or whatever the actual app-shell/auth routes are — check `app/` for the full non-marketing route list before finalizing); set `sitemap: `${config.app.baseURL}/sitemap.xml`` using the existing `config.app.baseURL` from `lib/config.ts`.

2. **No `sitemap.xml` route at all.** Neither `app/sitemap.ts` nor `public/sitemap.xml` exists. Marketing pages (home, pricing, solutions index, all 11 solution slugs, demo) have no machine-readable list of canonical URLs and last-modified hints for crawlers to discover and prioritize. **Why it matters:** a sitemap is the standard way to ensure all indexable URLs — especially the 11 dynamically-generated `/solutions/[slug]` pages, which have no other page linking to all of them in one place except the solutions index — get discovered and recrawled efficiently. **How to close:** add `app/sitemap.ts` exporting a `MetadataRoute.Sitemap` function. Static entries for `/`, `/pricing`, `/solutions`, `/demo`; dynamically map `SOLUTIONS` from `lib/solutions.ts` (already imported by `solutions/[slug]/page.tsx` via `SOLUTIONS.map((solution) => ({ slug: solution.slug }))` in `generateStaticParams`) into `/solutions/${slug}` entries so the sitemap and the actual static params can never drift apart. Use `config.app.baseURL` for the base.

3. **Zero structured data (JSON-LD) anywhere in the marketing site.** Repo-wide grep for `application/ld+json` and `schema.org` returns nothing. No `Organization`, `SoftwareApplication`, `FAQPage`, or `BreadcrumbList` markup exists. **Why it matters:** structured data is how search engines understand entity identity (Organization: name, logo, sameAs social links) and unlock rich results — FAQ rich snippets directly in search results, software-product rich results (rating/price/category), and breadcrumb trails in the SERP instead of a bare URL — per schema.org's own type definitions for `SoftwareApplication` (properties like `applicationCategory`, `offers`, `aggregateRating` exist specifically to power these enhanced listings) and `FAQPage`/`BreadcrumbList`, which are the standard vocabulary Google's structured-data documentation builds its FAQ and breadcrumb rich-result eligibility on. **How to close, four separate additions:**
   - **Organization** — add a JSON-LD `<script type="application/ld+json">` in `app/layout.tsx` (site-wide, since Organization identity doesn't change per page) with `name: config.app.title`, `url: config.app.baseURL`, `logo`, and `sameAs` (social profile URLs, once they exist).
   - **SoftwareApplication** — add to `app/(marketing)/page.tsx` (the homepage, as the canonical product page) with `name`, `applicationCategory` (e.g. "BusinessApplication" or "FinanceApplication"), `description` (reuse `config.app.description`), and `offers` once `pricing/page.tsx` has real tiers (currently a placeholder per its own TODO comment — see gap 9). Skip `aggregateRating` until there are real, disclosable reviews; a fabricated rating would violate Google's structured-data guidelines and schema.org's own expectation that this represents actual aggregated review data.
   - **FAQPage** — add to `app/(marketing)/page.tsx`, generated directly from the existing `QUESTIONS` array in `components/marketing/landing/faq.tsx` (export `QUESTIONS` from that file, or a mapped subset, and serialize it into the `mainEntity` array of `Question`/`acceptedAnswer` pairs) so the visible FAQ and the structured data can never disagree.
   - **BreadcrumbList** — add to `app/(marketing)/solutions/[slug]/page.tsx` inside `generateMetadata` or the page body (Home → Solutions → `{solution.name}`), since this is the one route with real hierarchical depth in the marketing site.

4. **No canonical URLs set on any page.** Repo-wide grep for `canonical` in `app/`, `lib/`, `components/` turns up zero hits related to metadata (all matches are unrelated domain concepts like "canonical supplier name"). No page sets `alternates.canonical` in its `Metadata` export. **Why it matters:** without an explicit canonical, Next.js/search engines infer one from the request URL, which is normally fine for these routes today — but it becomes a real risk the moment query-string variants exist (the homepage already has one: `?variant=a/b/c` for `LandingPagePrototype`, gated to non-production but a precedent for future query params), or if the site is ever reachable on more than one host/protocol combination. **How to close:** add `alternates: { canonical: "<path>" }` to each route's `Metadata` export (or `generateMetadata` for the dynamic slug route), built from `config.app.baseURL` + the route path, so it's explicit rather than inferred.

5. **No dedicated Open Graph image per page — every page shares the same implicit default.** `app/layout.tsx` defines `openGraph`/`twitter` blocks with title/description but no `images` array, and no `app/opengraph-image.*` or `app/(marketing)/*/opengraph-image.*` file exists anywhere (checked both the Next.js file-convention path and a manual `images` property in `lib/config.ts`, which has none). Every marketing page — home, pricing, solutions index, all 11 solution pages, demo — will render a link preview with no image at all (or a generic browser fallback) when shared on Slack, LinkedIn, X, etc. **Why it matters:** OG/Twitter image presence measurably affects click-through on shared links and is the single highest-visual-impact gap here, since it's the first thing anyone sees when a link to any of these pages is pasted anywhere. **How to close:** add `app/(marketing)/opengraph-image.tsx` using Next.js's built-in `ImageResponse` (App Router file convention — auto-wires into `openGraph.images` and `twitter.images` without touching `page.tsx` metadata) for a shared brand-default image, and optionally a per-solution `app/(marketing)/solutions/[slug]/opengraph-image.tsx` that renders `solution.name`/`solution.title` dynamically for sharper previews on the 11 solution pages.

6. **`app/(marketing)/layout.tsx` forces `export const dynamic = "force-dynamic"` on every marketing route, including fully static ones.** This is there for a real reason — the layout does a session lookup (`getSession()`) to decide the nav's signed-in state — but it means `pricing/page.tsx`, `solutions/page.tsx`, and the homepage `app/(marketing)/page.tsx` (none of which have per-request data needs of their own) are opted out of static generation and ISR caching at the route level, even though `solutions/[slug]/page.tsx` already proves static generation works for marketing content via `generateStaticParams`. **Why it matters:** CWV risk — `force-dynamic` means every request pays the ~2.5s-capped session lookup (per the code comment in that file) and a fresh server render, instead of serving a cached static/ISR response, directly inflating server response time (TTFB), which is upstream of LCP. web.dev's LCP guidance treats server response time as one of the four sub-parts of LCP that should each be minimized. **How to close:** this is an architecture trade-off, not a one-line fix — options to evaluate (not to implement here): (a) move the session-dependent nav state into a client-side fetch/RSC island so the page shell itself can be statically generated, or (b) confirm the existing 2.5s timeout and failure-tolerant fallback (already documented in the file's own comment) keeps worst-case latency acceptable and treat this as an accepted trade-off rather than a bug — but it should be a deliberate decision, not a default inherited from an unrelated need (nav personalization) forcing the entire homepage dynamic.

7. **9 of 18 homepage sections are Client Components (`"use client"`), on a homepage that is also fully server-dynamic per gap 6.** Grep of `components/marketing/landing/*.tsx` shows exactly half of the stacked sections opt into client-side rendering. Not inherently wrong — interactive sections (accordions, tabs, animated demos) legitimately need it — but combined with zero images and no bundle-size check having been done here, this is a documented risk, not a measured one. **Why it matters:** client-rendered sections add hydration JS to the homepage's main thread work, which is the mechanism most likely to hurt INP (web.dev's interactivity metric, good threshold ≤200ms) on a page that already stacks 18 sections. **How to close:** without a bundle analyzer run (out of scope for this static read), the concrete action is to audit which of the 9 client components could be server components with a smaller client "island" inside them (e.g., only the interactive control, not the whole section), and to add `next/dynamic` lazy-loading with `ssr: false` for any below-the-fold client sections that aren't needed for first paint (e.g., `Comparison`, `Faq`, `Library`, `MultiCurrency` are all well below the fold per their order in `app/(marketing)/page.tsx`).

8. **The homepage stacks 18 sections in one server-rendered tree with no visible lazy-loading/code-splitting boundary.** `app/(marketing)/page.tsx` imports and renders all 18 section components unconditionally, top to bottom, with no `next/dynamic`, no `loading="lazy"` equivalent, and no suspense boundary splitting above-the-fold from below-the-fold content. **Why it matters:** this is a static-code risk read, not a measured one — see the ticket's own scope note that this is not a Lighthouse run — but a monolithic 18-section import graph rendered fully server-side on every request (per gap 6) is the shape of page that tends to produce larger unused-JS-on-load and higher main-thread work, both of which web.dev's LCP/INP guidance flags as compounding risk factors, especially on the CWV metrics that are measured over the full page lifecycle, not just above-the-fold. **How to close:** wrap sections below roughly the 3rd–4th fold (`Pipeline` onward, by the order in `page.tsx`) in `next/dynamic()` imports, and/or `React.lazy` + `Suspense` boundaries, so the initial HTML/JS payload for LCP-critical content (`Hero`, `ReadsStrip`, `Proof`, `HowItWorks`) is decoupled from the long tail.

9. **`pricing/page.tsx` is an explicit placeholder** (its own comment: `TODO(product): replace the tier grid below with real plans and numbers before public launch`), which blocks the `SoftwareApplication.offers` structured-data field from gap 3 and means the pricing page's content itself (not its metadata, which is fine) isn't yet something worth deeply optimizing for search — flagging here only so it's sequenced correctly relative to gap 3, not as a new independent SEO gap.

## Prioritized closing plan

- **P0 — crawlability foundation (do first, no dependencies on anything else):**
  1. Add `app/robots.ts` (gap 1).
  2. Add `app/sitemap.ts`, sourced from `lib/solutions.ts` `SOLUTIONS` so it can't drift from the real routes (gap 2).
  3. Add `alternates.canonical` to every marketing route's metadata (gap 4).

- **P1 — rich-result and share-preview wins (high visible payoff, no architecture changes):**
  4. Add Organization JSON-LD to `app/layout.tsx`, FAQPage JSON-LD to `app/(marketing)/page.tsx` sourced from the existing `QUESTIONS` array, and BreadcrumbList JSON-LD to `app/(marketing)/solutions/[slug]/page.tsx` (gap 3, minus SoftwareApplication).
  5. Add `app/(marketing)/opengraph-image.tsx` (shared default) and a dynamic variant for `solutions/[slug]` (gap 5).

- **P2 — CWV risk reduction (needs a measurement pass before/after to confirm impact; higher engineering cost):**
  6. Evaluate the `force-dynamic` trade-off on `app/(marketing)/layout.tsx` and decide deliberately whether to keep it, cap the timeout tighter, or split nav personalization into an island (gap 6).
  7. Audit the 9 client-component homepage sections for server/client-boundary narrowing and lazy-load candidates below the fold (gap 7, gap 8).

- **P3 — blocked on product decisions, not code (sequence after pricing is real):**
  8. Once `pricing/page.tsx` has real tiers, add the `SoftwareApplication` JSON-LD with a real `offers` object (gap 3's SoftwareApplication piece, gap 9).
